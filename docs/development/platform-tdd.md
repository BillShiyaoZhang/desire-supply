# 目标平台测试驱动交付规范

> 状态：目标平台强制性交付规范
> 适用范围：从第一个平台 API 到生产化、迁移与恢复演练
> 不取代：当前 `mvp/` 的具体测试说明

本规范把“设计先行、测试驱动、垂直切片交付”变成可审计的工程门禁。它落实 [ADR-0001](/decisions/0001-platform-scope-and-delivery.md) 的交付方式：平台能力可以在隔离的开发和测试环境中完整实现，但通过测试不等于已获准处理真实身份、资金或争议。

## 1. 规范语义

本页使用下列强度：

- **必须**：不满足就不得合并或不得进入下一质量门禁；
- **应**：默认必须满足，偏离时需在设计或 ADR 中说明理由、风险和补偿控制；
- **可以**：允许团队根据技术栈和切片风险选择。

本规范保护的不只是返回值，还包括会影响参与资格、报酬、资金、隐私、申诉和历史可复现性的业务不变量。行覆盖率和用例数量只是诊断信号，不能代替对守卫、拒绝路径和可见性边界的证明。

## 2. 交付单位：垂直切片

一个切片是一条可由角色发起、跨过必要应用与数据边界、并产生可观察结果的最小能力。“先建所有表”、“先建通用 Repository”或“先写页面骨架”都不算切片。

每个切片必须在开始实现前写明：

- 目标角色、业务结果与显式非目标；
- 要求 ID、设计 ID 和可执行验收场景；
- 命令、状态、守卫、事件和不变量；
- 角色、资源关系、字段可见性和安全保持失败方式；
- 幂等、并发、超时、重试、降级、人工接管和回滚语义；
- 所需的测试层次、测试数据和发布/启用开关。

当上述任一结论会实质改变业务行为时，不得由实现者在代码中暗自选择；必须先补设计或 ADR。

## 3. REQ → DESIGN → TEST → CODE 追踪

### 3.1 稳定标识

| 类型 | 格式 | 示例 | 含义 |
| --- | --- | --- | --- |
| 需求 | `REQ-<AREA>-NNN` | `REQ-INVITE-004` | 用户结果、业务规则或质量要求 |
| 设计 | `DES-<AREA>-NNN` | `DES-INVITE-007` | 命令、状态、权限、数据或故障设计 |
| 测试 | `TEST-<LEVEL>-<AREA>-NNN` | `TEST-PROP-INVITE-003` | 可执行证据；`LEVEL` 如 `UNIT/PROP/DB/API/AUTH/EVENT/E2E` |
| 实现 | `CODE-<AREA>-NNN` | `CODE-INVITE-002` | 实现模块、公开符号或迁移 |

ID 一经评审不得重用。已取消的 ID 保留并标记 `superseded` 及替代项，不用重排编号美化文档。

### 3.2 追踪表格

每个切片的权威设计页必须维护如下表格。路径后使用标题、测试名或符号，不使用容易漂移的行号。

| REQ | DESIGN | 验收 | TEST | CODE | 证据/状态 |
| --- | --- | --- | --- | --- | --- |
| `REQ-INVITE-004` | `DES-INVITE-007` · `architecture/platform-domain-model.md#Invitation` | 重复响应不会产生第二个决定 | `TEST-PROP-INVITE-003` · `tests/property/test_invitation.py::test_response_is_idempotent` | `CODE-INVITE-002` · `application/invitations.py::respond` | `green` · CI 证据链接/构建 ID |

规则如下：

- 一个 REQ 可以对应多个 DESIGN 和 TEST，但不能没有反向链接；
- 一个测试可以保护多个要求，但测试名或元数据必须列出对应 TEST ID；
- CODE 列要指向业务入口、策略或迁移，不只写整个目录；
- `planned` 可进入设计评审，`red` 才可开始生产实现，`green` 表示局部行为通过，`verified` 表示所有适用门禁通过；
- `N/A` 不能单独出现，必须链接设计中的不适用理由。

## 4. 红—绿—重构证据

### 4.1 红：先证明缺少行为

实现前必须有至少一个与当前最小验收场景对应的失败测试。红灯有效需同时满足：

- 失败原因是预期业务行为尚未实现，不是语法错误、缺依赖、环境坏掉或 fixture 无效；
- 断言可以区分“未实现”与“实现了错误语义”；
- 记录 TEST ID、执行命令、退出状态和关键失败摘要；
- 如修复缺陷，测试必须先在未修复版本上稳定重现缺陷。

不要故意在测试中写错值来制造红灯。证据可由 PR/CI 摘要保留，不要为了存截图而提交重复构建产物。

### 4.2 绿：最小正确实现

绿灯阶段只实现当前验收场景需要的规则。不得通过删除断言、放宽 schema、关闭权限、跳过异常或在生产代码中识别测试环境来变绿。

绿灯证据至少包含：

- 新测试通过；
- 受影响模块的快速回归通过；
- 相同 TEST ID 的拒绝、边界和重复请求用例已补齐；
- 追踪表从 `red` 更新为 `green`。

### 4.3 重构：保持外部行为

重构前后必须使用同一套对外契约和黄金不变量。可以改变内部结构，不得在没有新 REQ/DESIGN/TEST 的情况下改变状态、错误码、可见字段、事件或幂等语义。重构后运行受影响回归和完整门禁，并审查测试是否过度耦合私有实现。

### 4.4 例外

- 探索性 spike 可以暂时不按红绿循环，但不得直接合并为生产实现；
- 生成代码由生成器和 schema 契约测试保护，不要为每个机械行写单元测试；
- 紧急安全修复应先写回归测试；当时确实无法安全重现时，必须记录原因，并在修复合并后第一个变更中补齐；
- 任何例外都不能跳过隐私、资金或授权的安全保持检查。

## 5. 测试层次与目录

目标平台代码根目录确定后，必须保留下列逻辑层次。语言和框架可以改变文件扩展名，不得把所有测试压成一个无法分层执行的目录。默认布局为：

```text
platform/
├── contracts/
│   ├── api/                 # OpenAPI / JSON Schema
│   ├── events/              # 版本化领域与集成事件 schema
│   └── providers/           # 支付、身份、通知、存储端口契约
└── tests/
    ├── unit/
    │   ├── domain/
    │   └── policy/
    ├── property/             # 性质与模型状态机
    ├── application/          # 用例编排与端口交互
    ├── integration/
    │   ├── database/
    │   ├── object_storage/
    │   └── queue/
    ├── contract/
    │   ├── api/
    │   ├── events/
    │   └── providers/
    ├── authorization/
    ├── security/
    ├── fault/
    ├── migration/
    │   └── fixtures/
    ├── e2e/
    ├── accessibility/
    ├── performance/
    ├── recovery/
    └── support/
        ├── builders/
        ├── fakes/
        └── golden/
```

| 层次 | 主要证明 | 默认依赖 | PR 中的要求 |
| --- | --- | --- | --- |
| 领域单元 | 规则、值对象、守卫、拒绝原因 | 无网络、无真实数据库 | 必须，快速执行 |
| 性质/状态模型 | 任意有效序列下不变量仍成立 | 可注入时钟、ID 和随机种子 | 新增状态或金额规则时必须 |
| 应用用例 | 编排、权限调用、事务边界意图和端口交互 | 内存端口/fake | 必须 |
| 基础设施集成 | SQL、索引、约束、对象存储和队列语义 | 与生产同类的真实服务 | 受影响适配器必须 |
| 契约 | API、事件与供应商边界的可兼容性 | schema 验证器、mock/sandbox | 边界变更必须 |
| 授权/安全/故障 | 默认拒绝、字段隔离、攻击面和安全降级 | 隔离环境 | 高风险切片必须 |
| E2E/无障碍 | 角色可完成真实任务且界面可用 | 部署应用 + 模拟/沙箱供应商 | 用户可见切片必须 |
| 性能/SLO/恢复 | 容量、可观测、恢复时间和数据一致性 | 近生产环境 | 发布/真实启用前必须 |

共享 helper 只能构建数据、驱动端口或比较结果，不能把被测业务规则在测试侧重新实现一遍。

## 6. 领域状态机与性质测试

每个有生命周期的聚合必须有设计中的转换表和测试中的参考模型。对每个命令至少覆盖：

1. 每个允许的起始状态、目标状态和事件；
2. 相邻和非法状态的拒绝，及稳定原因代码；
3. 等号边界、空值、过期时间、金额与版本边界；
4. 同一命令重复投递的幂等结果；
5. 两个合法但互斥命令的并发结果；
6. 审计事件中的 actor、resource、版本、原因与时间；
7. 失败时聚合、审计和 outbox 都不得留下半成品。

性质测试应生成有效与故意无效的命令序列，并在每一步比较参考模型与实现。至少保护：

- 已接受、已结算或已裁决的历史不被静默重写；
- 金额守恒，费用、净额、退款和冲正使用明确币种与最小单位；
- 被硬过滤者、未被邀请者或无权者不会经由另一命令绕过守卫；
- 规则、协议、档案和资源版本单调增长；
- 确定性规则在相同输入、时钟和版本下产生相同结果。

失败时必须输出可重现的随机种子和收缩后的最小反例。测试不得直接读取系统当前时间、生产随机数或网络。

## 7. 数据库事务与并发

持久化测试必须使用与生产同类、且主版本一致的 PostgreSQL。SQLite 或内存 Repository 可用于快速用例测试，不能证明 SQL、索引、隔离级别或并发语义。

每个写用例至少验证：

- 聚合状态、审计事件和 outbox 在同一事务中成功或一起回滚；
- 数据库约束与领域拒绝语义一致，不将原始 SQL 异常泄露给客户端；
- `Idempotency-Key`、provider event ID 和业务唯一键在并发下仍只产生一个事实；
- 乐观版本冲突返回明确错误，不丢失更新、不后来者静默覆盖；
- 两个 worker 同时取任务、邀请同一候选人、接受同一交付或处理同一付款不会重复产生副作用；
- 死锁、序列化冲突和短暂断线的重试有上限，且对外幂等；
- 组织、项目和私密字段在直接查询、关联、搜索、分页和缓存中都不跨租户泄露。

并发测试必须真正交叠事务，不只是顺序调用两次。每个测试使用独立 schema/数据库或可证明的清理机制，且必须能并行运行。

## 8. API 与 schema 契约

API 端点实现前必须有版本化 OpenAPI 和相关 JSON Schema。测试不只验证示例，而要验证实际请求、响应和错误对象与 schema 一致。

每个端点的契约测试至少包含：

- 最小合法请求、完整请求、未知字段、未知 enum、错误类型和超限大小；
- 稳定错误代码、人类可读摘要、字段问题和 trace ID，而非框架堆栈；
- 未认证、已认证但无权、资源不存在与资源存在但不可披露的语义；
- `Idempotency-Key`、`If-Match`/资源版本、重放、冲突和超时后查询；
- 分页稳定顺序、过期/篡改游标、空页和授权过滤后的页面语义；
- 金额最小单位、币种、UTC 时间戳、业务日期与时区边界；
- 读取 DTO 只含接收者允许字段，不直接序列化数据库对象；
- API 实现中每个已声明响应和错误都能在契约中找到，契约中也没有永不可达的伪分支。

契约变更必须运行自动兼容性差分。删除、缩窄类型、改变默认值、重解释错误或更改事件语义都按破坏性变更处理，需新版本和迁移/并行消费策略。

## 9. 授权矩阵与字段泄漏

每个资源必须先在设计中建立下列维度的授权矩阵：

```text
actor role × organization/project relationship × resource state
           × action × field visibility × safety hold
```

测试由矩阵生成或参数化，默认拒绝。每个允许用例至少搭配：一个同角色但无资源关系的拒绝用例、一个相邻状态拒绝用例、一个字段级脱敏用例。

字段泄漏测试必须检查：

- HTTP 正常响应、错误响应、分页、搜索和导出；
- 领域/集成事件、outbox、死信、通知模板和 webhook 日志；
- 应用日志、跟踪属性、指标标签、异常监控和调试页；
- 缓存键/值、对象存储元数据、预签名 URL 和分析投影；
- 私密报酬底线、身份材料、安全举报正文、未披露评价与第三方资料。

运营后台和代理操作不允许使用“超级用户全通”作为测试默认。必须验证职责、工单、理由、双人批准、时效和审计中适用的组合。

## 10. Outbox、Inbox 与 Webhook

### 10.1 Outbox / Inbox

事件驱动边界默认假设“至少一次投递”，不假设 exactly-once。必须测试：

- 业务状态和 outbox 原子提交；
- 事件 ID、聚合 ID、聚合版本、schema 版本和因果/跟踪 ID 完整；
- worker 在发送前、发送后但标记前崩溃时的重投行为；
- inbox/消费者依事件 ID 去重，副作用不重复；
- 同聚合乱序、跨聚合无序和延迟消息的明确处理；
- 指数退避、最大次数、死信、人工重放和重放审计；
- 通知、搜索和分析失败不回滚已成功的交易事实。

时钟、退避和 worker 竞争必须可控，测试不使用真实长时间 `sleep`。

### 10.2 外部 Webhook

每个供应商 webhook 适配器至少覆盖：

- 有效签名、无效签名、缺签名、过期时间窗口和密钥轮换重叠期；
- 重复 event ID、同一业务事实的不同 event ID、乱序和延迟事件；
- 未知事件类型、新增字段、缺必要字段、错误类型和超大 payload；
- 供应商对象、币种、金额、协议版本或账户不匹配时安全停止；
- 平台返回超时后供应商重试，以及平台处理完成但响应丢失；
- 外部状态与本地投影不一致时进入对账/人工队列，而不猜测成功。

完整 webhook payload 不得无限期进入通用日志。如因取证需要保留，必须测试加密、授权、保留期和删除语义。

## 11. 供应商契约

身份验证、支付、签署、邮件/通知、对象存储、文件扫描与 AI 供应商都必须通过端口隔离。每个端口有三组共享契约：

1. **本地 fake 契约**：快速、确定、可注入故障；
2. **适配器契约**：验证平台领域语义与 SDK/HTTP 映射；
3. **供应商沙箱契约**：使用供应商沙箱证明对方真实行为未漂移。

fake 不得比真实供应商更宽松。错误分类至少覆盖可重试、不可重试、结果未知、需人工审查和供应商已接受但本地超时。必须测试限流、超时、部分响应、畸形响应、临时不可用和凭据失效。

沙箱测试与日常 PR 的无网络测试分开，但真实启用前必须有对当前提交有效的最新成功证据。测试不使用生产凭据、真实身份或可结算资金。

## 12. 安全测试与故障注入

安全测试从切片的威胁模型和数据分类产生，不在交付末期只运行一次通用扫描。适用时必须覆盖：

- 账户枚举、会话固定/撤销、凭据重放、恢复流程和 MFA 高风险动作；
- CSRF、CORS、重定向、注入、SSRF、路径/对象越权和请求大小限制；
- 文件类型伪造、恶意内容、扫描失败、预签名 URL 过期和不同用户对象访问；
- 速率/配额限制、邀请和消息滥用、批量枚举和高成本 AI 请求；
- 提示注入、模型输出伪造工具/规则指令、私密项目数据路由和禁止 AI 时的安全降级；
- token、密钥、私密底线、身份材料和完整 webhook 正文在日志/异常中的脱敏；
- 依赖、容器/镜像、前端资产和部署产物的可重复锁定与已知漏洞检查。

故障注入至少放在事务提交前后、outbox 发送前后、对象上传的各阶段、供应商已接受但响应丢失、缓存/搜索不可用和 worker 被终止的位置。对每个故障断言：

- 业务事实是“成功”、“失败”还是“结果未知”；
- 客户端不会因重试产生第二个资源或金额变动；
- 系统会重试、降级、暂停新开工或进入人工队列，不猜测外部成功；
- 告警、跟踪、审计和操作手册能够识别并处理该状态。

## 13. 迁移、兼容与差分测试

每个数据库迁移必须对以下起点运行：空库、当前上一版、所有受支持的历史基线和含边界/大量数据的固定 fixture。

迁移测试必须证明：

- `expand -> migrate/backfill -> contract` 每阶段可重复执行；
- 滚动发布期间新旧应用版本的最小兼容窗口；
- 应用回滚不假设数据库会自动回退；
- 行数、关键金额合计、状态分布、外键、不变历史和审计链的差分结果可解释；
- 未知 enum、损坏记录、缺失版本、中断后重跑和部分回填安全失败；
- 已接受交付、已结算资金、已发布规则与历史推荐不被重写；
- 删除、法定保留、备份过期和导出语义覆盖新表、快照、缓存和对象。

从当前 MVP 迁移或复用规则时，使用虚构黄金批次运行新旧引擎差分。差分至少比较：输入接受/拒绝、预算评估、硬过滤原因、排序、解释投影、规则复合版本和隐私不变量。所有预期差异都必须绑定新 REQ/DESIGN，不用“新系统就是不一样”接受无法解释的漂移。

## 14. 端到端与无障碍

### 14.1 端到端

E2E 保护少量高价值用户任务，不复制所有领域边界测试。完整平台至少包含以下可组合场景：

1. 需求草稿 → 验证 → 资金保障 → 匹配 → 邀请 → 双向选择；
2. 协议确认 → 里程碑开工 → 交付 → 修改/验收 → 结算 → 双盲评价；
3. 创作者拒绝、无合格候选人、协议未成立和资金失效的无成交路径；
4. 变更单影响价格/时间并需受影响方重新确认；
5. 交付争议 → 调解/裁决 → 申诉或外部救济记录；
6. 供应商不可用、重复 webhook、通知延迟和 worker 重启后的可恢复路径；
7. 数据导出、更正、删除/保留冲突和安全暂停的数据权利路径。

E2E 使用每次新建的随机业务 ID 和虚构资料；不依赖测试顺序，不读取其他测试留下的数据，不用固定 `sleep` 等待异步结果。

### 14.2 无障碍

用户可见的每个切片默认以 WCAG 2.2 AA 为验收基线；偏离需记录 ADR。自动测试至少检查语义结构、可访问名称、表单标签/错误关联、焦点可见、对比度和明显规则违反。还必须用真实键盘测试：

- 登录/恢复、创建需求、响应邀请、确认协议和提交/验收交付物；
- 对话框、错误摘要、动态状态、超时警告和焦点恢复；
- 不依靠颜色或指针手势的状态与操作。

自动扫描不能替代对关键流程的辅助技术人工演练。首次真实启用前，至少用一组选定的屏幕阅读器/浏览器组合验证关键流程，并记录已知限制。

## 15. SLO、性能与可观测性

测试不自行发明流量、延迟和恢复目标。每项性能断言必须链接 REQ/DESIGN 中的用户量、请求分布、数据规模、突发比例和服务级别目标。目标平台的整体可用性方向见 [目标平台架构](/architecture/target-platform.md#可靠性与可观测性)，但每个切片仍需定义自己的 SLI 和错误预算影响。

适用时必须验证：

- API 延迟/错误、匹配耗时、队列停留、webhook 新鲜度、验收响应和结算时间；
- 目标吞吐、峰值、持续压力与队列积压后恢复；
- 分页深度、大组织/项目、长历史、大文件元数据和报表时间窗；
- 调用链有 trace ID，写入包含 actor ID、resource ID、规则/协议版本和结果代码；
- 重试、死信、对账差异、权限拒绝和数据删除失败有可操作告警；
- 日志、trace 和指标不把高基数业务 ID 无界加入指标标签，也不包含私密字段。

PR 性能测试只负责抓明显回归。SLO 是预发布和生产时间窗上的观测结论，必须配合合成监控、真实告警路由和错误预算，不能用一次本地 benchmark 宣称达标。

## 16. 备份与恢复演练

首次真实启用前以及备份、加密、存储或关键 schema 发生变化后，必须把真实备份恢复到隔离环境并演练，不得只检查“备份文件存在”。

恢复验收包含：

- 从备份开始到服务可安全接管的时间不超过设计 RTO；
- 最后可恢复事实与故障点的差距不超过设计 RPO；
- 密钥、数据库、对象版本、审计、outbox/inbox 和规则版本都可读；
- 恢复后的重放不会重复通知、邀请、资金或外部副作用；
- 平台投影与支付/身份等供应商事实完成对账；
- 核心 E2E、权限矩阵抽样、数据库完整性和隐私泄漏检查通过；
- 备份中的删除/保留到期语义与设计一致。

演练记录包含备份时点、故障假设、参与人、步骤、实际 RPO/RTO、完整性结果、对账差异和改进责任人。测试与操作手册必须使用同一套恢复命令，避免只有测试环境能恢复。

## 17. 测试数据、可重现性与不稳定测试

- 测试资料必须虚构；禁止由生产库、真实身份、合同、付款或争议材料直接导出；
- builder 默认生成最小合法对象，每个测试只显式改变与当前行为有关的字段；
- 时钟、ID、随机、地区/时区、规则版本和供应商响应可注入；
- 黄金数据优先锁定原因代码、状态、分项、金额、事件 schema 和可见性，避免大段锁定可合理改动的中文文案；
- snapshot 更新必须逐项评审，不得使用批量重录掩盖行为漂移；
- 测试失败输出随机种子、时钟、业务 ID、规则/schema 版本和必要的脱敏跟踪。

任意失败用重试就隐藏的测试视为失败。不稳定测试必须有责任人、原因、复现证据和修复时限；涉及资金、授权、隐私、迁移或恢复的测试不得隔离为非阻塞项。

## 18. 切片质量门禁

每个切片依次通过下列门禁。后一门禁不会替代前一门禁。

| 门禁 | 必须证据 | 阻断条件 |
| --- | --- | --- |
| Q0 设计就绪 | REQ/DESIGN ID、验收场景、状态/权限/数据/故障设计、适用测试层 | 关键判断仍是“待实现时决定”；端口/schema 无版本 |
| Q1 红灯有效 | TEST ID、可重现命令、预期语义失败 | 测试因环境/语法/fixture 失败；先有生产实现后补测试 |
| Q2 领域绿灯 | 成功、边界、拒绝、重复命令和性质测试；受影响快速回归 | 守卫可被另一入口绕过；结果不确定；追踪仍是 `red` |
| Q3 边界绿灯 | 真实数据库事务/并发、API/event schema、授权矩阵、字段泄漏、适用的 provider 契约 | 仅用 in-memory fake 证明持久化；权限只有正例；有未解释契约破坏 |
| Q4 系统绿灯 | 关键 E2E、无障碍、异步重放、故障注入、可观测断言 | 只有 happy path；需固定 sleep/顺序执行才能通过；故障后结果不明 |
| Q5 可发布 | 全量回归、迁移、安全检查、性能回归、操作手册，追踪表为 `verified` | 存在无主的间歇失败；不能回滚/降级；证据不对应当前提交 |
| Q6 可真实启用 | 当前供应商沙箱、SLO 验证、恢复演练、隐私/法律/安全批准、人工降级演练 | 只有代码完成；缺司法辖区/供应商决策；真实启用开关无审批 |

合并通常要求 Q0–Q4；纯后端且未有用户界面的切片可将无障碍标记为有理由的 `N/A`。Q5 是发布候选门禁，Q6 是真实能力启用门禁。

### 18.1 切片附加义务

| 切片类型 | 不可跳过的附加测试 |
| --- | --- |
| 身份/组织/会话 | 账户枚举、恢复、MFA、会话撤销、组织越权、同意版本 |
| 档案/需求/匹配 | 字段可见性、硬过滤性质、确定性、规则差分、快照不变性、容量竞争 |
| 邀请/双向选择 | 重放、过期、撤回、并发接受、拒绝不降权、不可邀请被过滤者 |
| 协议/交付/验收 | 版本并发、受影响方重新确认、超时边界、变更单、文件安全、已验收历史不变 |
| 资金/账本/对账 | 金额性质、币种、webhook 签名/乱序/重放、退款/拒付、对账、供应商故障、恢复后去重 |
| 评价/举报/争议/治理 | 双盲截止、利益冲突、证据权限、程序期限、理由、申诉、AI 不可最终裁决、反报复 |
| 通知/搜索/分析 | 事件重放、权限过滤、删除传播、敏感字段不入索引/分析、不回滚主事务 |

## 19. CI 执行与证据

PR 默认按从快到慢的顺序执行：

1. 文档链接/导航、schema 格式和 REQ—DESIGN—TEST—CODE 完整性；
2. 静态检查、领域单元、性质与应用用例；
3. API/event 契约、授权矩阵和隐私泄漏；
4. PostgreSQL、对象存储、队列和迁移集成；
5. 关键 E2E、自动无障碍、故障注入和快速性能回归。

供应商沙箱、完整安全扫描、长时间压测和恢复演练可分开运行，但发布/真实启用必须验证证据来自当前提交或兼容性等价的不变产物。

每次构建摘要至少保留：

- commit 和不可变构建 ID；
- 各层次命令、通过/失败/跳过数及耗时；
- 失败 TEST ID、随机种子和脱敏摘要；
- schema/迁移/供应商契约版本；
- 适用门禁及有理由的 `N/A`；
- 差分、性能、安全和恢复产物的链接与保留期。

阻塞测试不得用自动重试变绿。测试隔离必须有明确审批和修复期限，且不能适用于资金、授权、隐私、迁移、安全或恢复门禁。

## 20. 切片完成清单

切片仅在以下各项都成立时可标记完成：

- [ ] 权威设计位于 `docs/`，关键决策无未解释冲突；
- [ ] 每个 REQ 都有 DESIGN、验收、TEST 和 CODE 反向链接；
- [ ] 红灯证据表明测试在实现前因预期语义失败；
- [ ] 成功、边界、拒绝、幂等、并发和故障路径已覆盖；
- [ ] 状态机、金额、版本和不变历史有性质/模型测试；
- [ ] 数据库原子性、并发、迁移、outbox/inbox 使用真实技术边界验证；
- [ ] API、事件和供应商契约已版本化，且无未解释破坏变更；
- [ ] 授权矩阵、租户隔离、字段可见性和输出/日志泄漏检查通过；
- [ ] 关键 E2E 和用户可见变更的无障碍验收通过；
- [ ] 观测可回答“谁对什么做了什么、使用哪个版本、结果为何”，且不泄露私密数据；
- [ ] 已定义发布、回滚、降级和真实启用开关；
- [ ] 全量适用测试和 `python3 scripts/verify_docs.py` 通过，追踪状态为 `verified`。

一个切片通过以上门禁，只证明其在已声明环境下按契约工作。真实身份、资金、协议、裁决或社区治理的启用，仍需 [ADR-0001](/decisions/0001-platform-scope-and-delivery.md#真实启用门槛) 定义的外部证据与批准。
