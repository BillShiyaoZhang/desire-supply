# 工程演进路线

本页说明工程如何支持[整体方案报告](/desire-supply-platform-design.md)与[Foundations 落地路线图](/foundations/realization-roadmap.md)的 R0–R3，不另设一套阶段 0–4。战略阶段决定优先验证什么，工程交付说明哪些能力实际可用；二者都不自动替代研究、服务或生产启用的授权条件。

## 从现有实现出发

当前已经有 `platform/` + `web/` 内部多角色工作台，以及独立的 `mvp/` CLI。账号、页面、画像、需求、审核与匹配等能力不能再被列作“未来才开始”的空白；也不能因此把内部沙箱写成已开放的真实平台。当前 Web 尚未接通项目协议、交付验收和结算的完整流程，作品与长期实践中心的新能力仍需设计。

工程工作的起点是固定版本上的能力核验：哪些已有契约，哪些有领域实现、持久化、HTTP 与前端入口，哪些完成装配、恢复验证及实际运行。现有事实与专题入口见[系统总览](/architecture/overview.md)。

## 对 R0–R3 的工程支持

| 合作与验证阶段 | 工程应支持的结果 | 最小交付与证据 |
| --- | --- | --- |
| **R0：合作准备** | 对齐作品、长期实践、两种早期入口、角色权利和人工承接方式 | 核对现有代码与装配；为共同定义委托、创作者发起各形成一个合成样例；识别新对象、权限、资金语义和能力缺口，更新需求到能力、用例与证据的映射 |
| **R1：最小完整创造循环** | 让获准的窄范围活动从问题和决定，走到可用成果、使用反馈、报酬与后续安排 | 复用已验证基础，逐项接通必要的协议、交付、文件、资金事实与保护路径；作品全貌、发起、贡献、使用反馈和权利先有可连续执行的安排，再产品化反复出错的环节 |
| **R2：持续使用与跨项目验证** | 证明成果、知识、关系和权利能够持续使用并带入下一次创造 | 建立必要的维护与持续服务记录、作品历史、选择性披露、可携带贡献材料及接收演练；记录换工具、暂停、移交和退出的实际结果 |
| **R3：共用基础设施与多节点治理** | 在共享需求和责任成熟后，支持公共知识、公共劳动、有限治理与节点协作 | 按获准范围逐项交付许可、维护、预算、提案、任期、冲突回避、申诉和承接机制；软件执行已成立的权利，不以字段或页面宣称共同所有已经实现 |

R1 的早期两种入口是共同定义委托与创作者发起作品。共同或公共创造是整体方案的一部分，其多人、资金、代表授权与共同权利按路线图条件逐步开放。阶段不按功能数量自动推进，也不要求一次性建设表中全部系统。

## 每个纵向切片怎样交付

先写清参与者要完成什么、谁能够决定什么、相关权利和事实由谁负责，再选择最少需要的软件。人工流程或外部工具可以承接尚未软件化的步骤，但必须有明确责任、可追溯记录和异常处理；不能把“人工可处理”当作未经验证的兜底承诺。

```mermaid
flowchart LR
    A["具体用例与权利边界"] --> B["契约、领域与权限"]
    B --> C["持久化、接口与用户入口"]
    C --> D["装配、恢复与异常验收"]
    D --> E["获准范围内运行"]
    E --> F["观察实际改善与负担"]
    F -. "修改、缩小或停止" .-> A
```

验收至少覆盖适用的正常、拒绝、撤回、冲突、故障、申诉和退出路径。通过领域测试不等于持久化完成，通过静态部署检查不等于生产执行，软件可运行也不等于创造者实际获得了更多自主权。

## 工程取舍

- **先保证完整理解和实质选择。** 作品不能只是需求或交付记录的新名称；需要区分一次合同、长期成果、使用反馈和后续维护，并表达不同参与者的决定权限。
- **基础保护与新能力共同交付。** 创作者发起、付费探索、共同反馈等路径开放时，同步具备适用的同意、报酬、纠错、救济和恢复；不把这些视为后续优化。
- **复用已有平台，不强行统一历史模型。** CLI 可继续用于其适合的运营工作；原型用于合成演练。迁移或集成前说明事实来源、数据范围与兼容方式，不默认三条代码路径彼此同步。
- **接入工具服务于作品控制。** 优先支持已有创作工具、清楚的费用与数据边界、材料携带和成果验证。R1 不以自建通用 AI IDE 或监控全部制作过程为前提。
- **按可复核证据安排优先级。** 优先修复使人失去权利、报酬、重要决定或成果连续性的问题；重复录入、版本失真和高运营负担应以实际发生的用例说明。
- **保留现实责任。** 支付、组织治理、许可与所有权需要相应主体、有效文件和可承担的运营能力；软件不能自行赋予这些事实。

## 阶段推进与停止

R0–R3 回答学习与协作的顺序，既有 P0–P5 保留制度激活语义，Gate 决定特定活动是否获准；三者不按编号机械对应。具体条件以[Foundations 路线图](/foundations/realization-roadmap.md)、[启动决策入口](/foundations/readiness-and-start-decision.md)和有效决定记录为准。本页不增加新的日期、项目数量或发布承诺。

每轮工程评审同时检查：真实开放了哪些能力、哪些仍由人工承担、故障与退出是否可恢复，以及这些变化是否改善重要决定的参与、实际使用、报酬、权利和负担。若增加无偿劳动、形成新的锁定、让救济不可达或超出服务容量，应修改或缩小范围；停止新增活动仍须履行已经承担的义务。

具体交付方法继续参考[开发与变更流程](/development/workflow.md)、[测试与质量](/development/testing.md)、[平台 TDD 交付规范](/development/platform-tdd.md)和[软件交付章程](/foundations/software-delivery-charter.md)。目标技术模型见[目标平台架构](/architecture/target-platform.md)，按其适用阶段与当前实现核对后采用。
