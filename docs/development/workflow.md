# 开发与变更流程

## 基本流程

1. 从问题和证据开始，写清这是软件缺陷、运营缺陷、数据缺陷还是尚未验证的想法。
2. 确定影响范围：隐私、报酬、资格、历史可复现性和真实批次是否受影响。
3. 先写或更新失败测试，明确预期不变量。
4. 做最小实现；避免同时改变字段、算法、配置和运营流程而无法归因。
5. 运行单元测试、文档校验和一条虚构数据端到端命令。
6. 更新对应设计、数据字典、模板或操作手册。
7. 审查差异中是否出现真实身份、付款、密钥或本地数据库。
8. 如果影响活动批次，按下文的冻结规则处理，不静默生效。

## 变更分类

| 类型 | 例子 | 最低验证 |
| --- | --- | --- |
| 纯重构 | 拆函数、不改变输出 | 全部测试 + 固定样例结果不变 |
| 缺陷修复 | 错误日期边界、泄漏漏检 | 失败回归测试 + 全部测试 |
| 输入 schema | 新字段、新 enum | 校验、样例、数据字典、迁移/兼容策略 |
| 硬过滤 | 新地域或安全边界 | 配置版本、正反例、原因文本、公平性审查 |
| 权重/公式 | 调整兴趣权重 | 批次证据、新配置版本、离线差分、批准记录 |
| 存储 schema | 新表/列/约束 | 旧库升级测试、备份恢复、删除影响 |
| 对外输出 | 候选说明、报告字段 | 隐私测试、接收者可见性审查 |
| 运营流程 | 同意、付款、争议步骤 | 模板/手册、责任人、演练、法律确认 |

## 规则版本化

规则文件一经用于真实推荐便不可覆盖。以修改预算为例：

1. 复制为 `budget-v2.yaml`；
2. 修改内部 `version`、`effective_date` 和 `provenance`；
3. 更新 `manifest.json` 的文件与声明版本；
4. 增加新边界测试和旧批次差分报告；
5. 在批次开始前记录启用决定；
6. 保留 `budget-v1.yaml`，确保旧快照可解释。

taxonomy、matching、reason codes 同理。复合 `rule_version` 会进入每个推荐快照。

## 活动批次冻结

一个五项目批次内默认冻结词表、预算、权重和原因代码。项目中途只修复阻塞性软件错误或明确安全问题。

如果必须修复：

- 记录受影响的命令、项目和旧结果；
- 判断是否需要重新运行，并向参与者解释影响；
- 以新版本配置或应用修订号保存，绝不覆盖旧推荐；
- 在批次报告中标注前后不可直接比较；
- 安全问题优先停止流程，不能为了保持实验一致性继续暴露风险。

## 数据 schema 演进

当前 JSON 没有显式 `schema_version`，因此新增必填字段会让旧资料立即失败。这是已知限制。下次做实质 schema 演进前应先增加：

- 每种记录的 `schema_version`；
- JSON Schema 或等价的机器可读契约；
- `v1 -> v2` 纯函数迁移器；
- 旧样例加载与迁移测试；
- 只读预检命令，迁移前不修改原文件；
- 备份、回滚和删除语义。

不要在 `Repository.get_entity` 中静默猜测旧格式，这会破坏复现。

## 数据库变更

`Repository.initialize` 当前包含一次向后兼容的加列逻辑。后续迁移增加后，应建立正式迁移表和单调版本号。迁移必须幂等，先备份，禁止删除列或重写历史快照，除非有明确的保留/删除义务和可恢复路径。

## 隐私审查清单

每个读取或输出数据的变更都回答：

- 谁是接收者，完成当前任务需要哪些字段？
- 是否把 match-only/private 字段变成了公开字段？
- 自由文本是否可能包含身份、歧视性判断或第三方信息？
- 日志、异常、测试快照和报告是否复制了敏感值？
- 删除请求能否覆盖新表、新快照、新缓存和备份？
- 外部服务是否得到新数据，是否需要新的同意和协议？

## 完成定义

代码变更至少满足：

- 行为测试覆盖成功、边界和拒绝路径；
- 真实规则变化具有新版本和来源说明；
- 相同输入结果确定，或明确记录为何不再确定；
- 对外输出通过私密字段和自由文本审查；
- 文档、样例、数据字典和 CLI 帮助同步；
- `python3 scripts/verify_docs.py` 与 MVP 全部测试通过；
- `git status` 中没有数据库、报告、联系人材料或秘密。
