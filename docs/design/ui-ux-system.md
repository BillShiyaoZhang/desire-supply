# 愿作 UI/UX 系统设计

> 设计基线：2026-09-04。适用于当前 `platform/` + `web/` 多角色工作台及其后续演进。
> 本文规定信息架构、交互和视觉方向，不作为功能已实现、浏览器验收通过或真实试点获准的证据。
> 除明确引用的外部规范外，本文的页面数量、分组数量、尺寸、断点与验收目标都是愿作的项目设计决策，不是 Apple 的强制要求。

## 1. 用户打开愿作，是为了推进一项合作

愿作帮助创作者找到愿意投入、能够做好、条件清楚的劳动机会，也帮助需求负责人把问题变成双方能理解和确认的协作。审核、资金确认、管理与救济围绕这条协作过程提供保障。

界面应持续回答四个问题：**我在哪里、现在发生了什么、需要谁行动、我接下来能做什么。** 默认先给出当前任务，再让用户查看依据和历史。技术状态和审计信息保留可达，但不成为每页的开场白。

当前主要问题是同一页同时承担导航、对象列表、多个角色工作台、长表单、历史与操作反馈。单个功能可能完整，合在一起却要求用户自行判断哪些内容与当前目的有关。本次设计把这些职责分开，并统一返回、状态与下一步的位置。

### 1.1 采用的 Apple 理念

Apple 当前的 [Design principles](https://developer.apple.com/design/human-interface-guidelines/design-principles) 强调目的、用户自主性、责任、熟悉感、适应性、简洁、细节与愉悦。愿作采用以下转译：

| 设计原则 | 愿作中的具体决定 |
| --- | --- |
| 先理解目的 | 导航使用“我的需求”“资金确认”等任务语言；首页从待办进入具体对象 |
| 保留用户自主性 | 可保存草稿、返回修改、拒绝邀请；任何接受、发布与裁决都由本人明确完成 |
| 对用户负责 | 说明资料可见范围、操作后果、结果未知与救济路径 |
| 使用熟悉模式 | 使用侧栏、列表详情、表单步骤、页内状态和明确返回入口 |
| 简洁且完整 | 减少同时展开的内容；关键条件、费用、期限和风险仍在决定前出现 |
| 适应上下文 | 大屏使用空间分层，窄屏按同一顺序逐页呈现，键盘与辅助技术都可完成操作 |

这些是针对愿作的设计推导。Web 界面采用系统字体和熟悉控件，不要求复制 Apple 硬件外形、原生控件材质或 Liquid Glass 效果。

### 1.2 当前范围与未来范围

当前范围以仓库 `web/README.md`、[本机工作流验收记录](../operations/local-workflow-ui-acceptance-2026-09-04.md) 和现有 Web 装配为准；产品职责以 [产品与首批试点定义](../foundations/product-and-pilot-definition.md) 为准。

| 范围 | 界面安排 | 不能表达成 |
| --- | --- | --- |
| 当前账号、政策确认、工作区、会话 | 进入工作台的准备流程与“账号与安全” | 公开注册平台 |
| 当前画像、需求、审核、合成资金确认 | 核心工作入口 | 真实资金到账、托管或支付 |
| 当前匹配审核、邀请响应、候选选择 | “协作”组中的独立工作入口 | 邀请接受即签约、选择完成即交付 |
| 当前组织、账号、Trust、Appeal、管理员需求全流程 | 按权限显示的管理或救济入口 | 管理员拥有所有业务操作权 |
| 后续项目、协议、里程碑、验收、支付 | 仅在流程说明中标注“尚未接入” | 可点击的空工作台或已完成阶段 |
| 公开注册、聊天、社区、真实合同与支付 | 不列入当前主要导航 | 用演示按钮假装已接通 |

固定的环境提示始终显示“内部试运行 · 仅使用合成资料”。“关于此工作区”提供 `INTERNAL_SANDBOX`、`G1 NO-GO / G2 NO-GO` 和禁止真人研究、真实合同、资金与支付的完整说明；涉及资金和授权的操作前继续显示相应边界。本文不改变任何 Gate。

旧 [本地合成多角色 ADR](../architecture/local-synthetic-multi-role-platform.md) 中的七角色 `J01..J12` 是另一运行路径，不能作为当前 Web 已实现完整合同和交付流程的依据。

## 2. 核心流程及其交接

### 2.1 参与者流程

| 流程 | 用户目标与顺序 | 每次交接要看见什么 |
| --- | --- | --- |
| 创作者准备 | 填写意愿与能力 → 设置时间、报酬与边界 → 检查 → 发布画像 | 画像是否可参与匹配、尚缺哪些资料、如何暂停 |
| 需求准备 | 说明问题 → 定义成果和验收 → 安排计划与预算 → 说明职责与边界 → 提交 | 提交的是哪个版本、现在由谁审核、能否修改 |
| 整改 | 查看具体原因 → 定位需要修改的部分 → 保存 → 检查变化 → 重新提交 | 原要求、当前修改和新提交结果相互对应 |
| 合作选择 | 运营发布邀请 → 创作者阅读并响应 → 授权选择者比较已接受候选 → 确认选择结果 | 邀请条件、截止时间、当前选择状态、后续协议尚未接入 |
| 救济 | 从自己的相关事项报告问题 → 查看处理状态和结果 → 符合条件时申请申诉 | 提交对象、处理责任、截止时间、可公开的理由与下一步 |

创作者的“拒绝邀请”使用清楚且不带惩罚暗示的措辞，拒绝理由维持可选和私密。邀请响应页必须同时可找到接受和拒绝，不通过按钮大小差异施压。

### 2.2 保障流程

| 流程 | 顺序 | 重要边界 |
| --- | --- | --- |
| 需求审核 | 队列 → 领取 → 阅读本次提交 → 记录整改或验证 → 查看结果 | 领取不等于批准；审核人不直接改写需求正文 |
| 资金确认 | 队列 → 领取 → 核对合成证据 → 独立确认 → 查看两人进度 | “已确认 1 / 2”与“两人确认完成”清楚区分；实际资金仍为零 |
| 匹配审核 | 领取分配 → 检查候选和理由 → 设置邀请 → 检查并发布 | 领取前不展示受限候选；评分只在获授权审核上下文出现 |
| Trust | 领取 → 查看报告 → 分诊与措施 → 检查并公布结果 | 涉及独立解除时进入另一名负责人的复核任务 |
| Appeal | 领取 → 阅读原决定 → 记录独立评估 → 检查并发布决定 | 原处理与申诉复核是不同职责；不能在 UI 中合并成“再次审核” |
| 管理 | 选择账号或组织 → 查看当前状态 → 执行一项明确操作 → 重读结果 | 账号管理、组织管理不自动带来审核、候选选择或财务权限 |

需求详情可用简明阶段条呈现“填写 → 审核 → 资金确认 → 合作选择”。被退回、取消或需处理的状态显示真实分支原因，不能用一个“完成百分比”代替。后续“协议 / 交付 / 验收 / 支付”只在流程全貌中明确标注尚未接入。

## 3. 信息架构：工作区 → 工作入口 → 对象 → 当前任务

### 3.1 全局壳

全局只保留品牌、当前工作区及职责、账号入口。工作区选择回答“为哪个范围做事”，不是随意切换权限的角色模拟器。单一工作区自动进入；多个工作区时使用服务端返回的可用范围。

桌面左侧显示“工作 / 协作 / 管理 / 个人”四类目的分组，主区域只呈现当前入口。“个人”容纳账号与安全等辅助入口。侧栏不再同时堆入所有对象和所有审核队列；对象集合在对应入口内部显示。

Apple [Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars) 建议保持清楚、简短的层级，并在层级较深时结合内容列表。愿作的导航采用以下结构：

```text
当前工作区：个人 / 组织 / 平台职责
├─ 工作
│  ├─ 待办
│  ├─ 我的画像 / 我的需求 / 需求审核 / 资金确认（按职责显示）
│  └─ 匹配审核 / 信任与安全 / 申诉复核（运营职责）
├─ 协作
│  ├─ 合作邀请 / 合作匹配（按能力显示）
│  └─ 举报与处理 / 申诉与复核（需求方）
├─ 管理
│  ├─ 组织管理 / 账号管理（按职责显示）
│  └─ 需求全流程（仅获授权管理员）
└─ 个人
   └─ 账号与安全（我的会话、退出登录）
```

“工作 / 协作 / 管理 / 个人”是组标题，不必各做一张汇总页。没有可用入口的组整体隐藏。不要让普通用户面对一整张角色清单；角色代码留在权限说明中，日常使用“创作者”“需求负责人”“资金确认员”等中文名称。

### 3.2 导航约定

- 一个导航项只改变当前工作入口。打开需求或案件只改变入口内部的选择，不把其他模块一起滚入视野。
- 对象详情具有“返回需求列表 / 返回审核队列”等明确返回入口；返回保留当前工作区内的筛选与位置。
- 当前页通过选中样式、文字和可访问属性表达。不能只靠背景色。
- 搜索先限定在当前列表；只有跨模块检索能力真实存在时才提供全局搜索。
- 主入口使用真实导航语义；同一页面内的视图切换使用按钮或正确的标签页语义，保留浏览器返回行为的可预期性。
- 切换工作区前处理未保存草稿和结果未知的操作；切换后清空旧对象并重新读取新范围，不能保留跨工作区的详情或受限历史。
- 在同一工作区切换入口时，保留已挂载模块中的输入和恢复状态，只显示当前模块。普通编辑草稿按原有规则保存到当前标签页；不能把“切换页面”误实现为丢弃表单。存在结果未知写入时，自动显示负责恢复的入口并锁定导航，先完成现有恢复流程。
- “账号与安全”始终容易找到。举报与申诉从已支持的参与者入口和相关对象可达；尚未实现的数据权或退出善后能力只提供真实说明，不能放置无效提交按钮。

### 3.3 八职责与对象分配矩阵

“待办”和“账号与安全”为共同入口。下表是可用能力的分组规则，最终可见性仍以当前工作区和对象能力为准。

| 当前职责 | 默认主要入口 | 第二目的入口 | 详情内主要任务 | 不应混入的内容 |
| --- | --- | --- | --- | --- |
| 创作者 `CREATOR` | 我的画像 | 合作邀请 | 维护画像、响应本人邀请 | 他人的画像、排序评分、管理员工具 |
| 需求负责人 `DEMAND_OWNER` | 我的需求 | 候选选择、举报与申诉 | 提交与整改需求、处理本人事项 | 审核自己的需求、替创作者接受 |
| 运营审核员 `OPERATIONS_REVIEWER` | 资料审核 | 匹配审核 | 领取并处理当前分配 | 财务确认、无分配的受限候选详情 |
| 资金确认员 `FINANCE_OPERATOR` | 资金确认 | 本人处理历史 | 核对证据并完成独立确认 | 真实余额、支付控制台、代另一人确认 |
| 组织管理员 `ORG_ADMIN` | 组织管理 | 需求全流程 | 管理本组织成员与邀请 | 平台全部账号、其他组织需求 |
| 账号管理员 `ACCESS_ADMIN` | 账号管理 | 需求全流程 | 管理可见账号、会话与临时职责 | 自动取得项目决定与财务权 |
| 安全处理员 `TRUST_OFFICER` | 安全处理 | 本人处理历史、独立复核分配 | 领取报告、处理措施与决定 | 未领取案件正文、同人自我复核 |
| 申诉复核员 `APPEAL_REVIEWER` | 申诉复核 | 本人处理历史 | 独立评估原决定并发布复核结果 | 参与原决定、申请人编辑字段 |

候选选择者与匹配审核者是当前账号对具体事项获得的分配，不是新增的可任意切换身份。资金两席与 Trust 独立复核也不能用一个下拉框模拟另一人。

## 4. 页面注意力预算

以下是愿作的项目约定，用于设计评审，允许有明确任务理由的例外。Apple [Layout](https://developer.apple.com/design/human-interface-guidelines/layout) 支持通过对齐、间距、逻辑分组建立层级；以下数量不是对 Apple 规范的逐字套用。

| 层级 | 默认内容 | 愿作默认预算 |
| --- | --- | --- |
| 页面 | 一个用户问题、一个清楚标题 | 一个主要任务 |
| 页首 | 标题、短说明、状态、下一步 | 一个强调主操作；通常不超过两个次操作 |
| 首屏内容 | 当前任务、关键状态、阻塞或摘要 | 二至三个主要信息区 |
| 一级导航 | 当前职责可用入口 | 通常三至六项；超出时按目的分组而非缩小文字 |
| 对象摘要 | 名称、状态、下一步、责任与时间 | 通常四至六个有决策价值的事实 |
| 列表行 | 能选出待处理对象的信息 | 主标题加两行摘要；完整依据进入详情 |
| 表单当前阶段 | 一个相关问题集合 | 通常二至三个领域分区；复杂分区可独占阶段 |

“一个主操作”用于突出当前最自然的下一步，例如“继续填写”“查看邀请”或“提交审核”。它不意味着必须把接受、拒绝等平等选择藏起来，也不要求给每个等待页面硬加一个主按钮。Apple [Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons) 讨论减少强调按钮和区分按钮职责，愿作进一步采用上述更严格的默认预算。

同一页不同时展开“完整流程说明、长列表、完整编辑器、所有历史、所有风险操作”。已经有一个清楚标题的区块不再加英文眉题重复解释其组件名称。

### 4.1 页面任务表

| 页面 | 用户需要回答的问题 | 默认展示 | 按需展开 / 进入下一层 |
| --- | --- | --- | --- |
| 待办 | 我现在先处理什么？ | 默认“待处理”视图、异常提醒、两个开始工作的常用入口 | 切换到“等待中”“已完成”，或进入具体工作台 |
| 我的需求 / 我的画像 | 我要继续哪一项？ | 名称、状态、更新或截止时间、明确下一步 | 正文、所有版本、逐条审计 |
| 需求 / 画像详情 | 这项内容现在怎样、我能做什么？ | 状态摘要、内容概览、下一步 | 编辑、历史、版本比较、状态管理 |
| 编辑页 | 当前这一步需要提供什么？ | 阶段导航、当前字段、保存状态 | 其他阶段、示例、补充选项 |
| 审核队列 | 哪一项需要我处理？ | 可领取项、本人处理中的项 | 领取后的资料全文与决定表单 |
| 审核详情 | 本次提交是否达到要求？ | 资料摘要、核对内容、单一决定区 | 旧版本、历史、释放分配 |
| 合作邀请 | 我愿意在这些条件下继续吗？ | 目标、成果、报酬条件、时间与边界 | 附加说明与历史；决定前关键条件不得隐藏 |
| 候选选择 | 已接受的候选中谁适合这项需求？ | 当前需求、安全候选卡、选择理由入口 | 允许披露的更多资料；禁止公开内部排序分数 |
| 资金确认 | 证据是否足以完成我这一席确认？ | 预算与实际合成资金的区别、证据、两席进度 | 核对历史、差异处理、释放 |
| 安全 / 申诉详情 | 当前事项需要什么处理决定？ | 当前分配、必要事实、处理或复核表单 | 受限附件、历次措施、允许披露的历史 |
| 组织 / 账号管理 | 我要对哪个对象做哪项管理？ | 集合、当前选中项、状态与有效职责 | 详细会话、职责记录、低频管理动作 |
| 需求全流程 | 卡在哪里，谁做过什么？ | 当前阶段、阻塞、下一责任人 | 参与者、按阶段筛选的时间线、记录范围 |
| 我的会话 | 哪些设备仍可访问我的账号？ | 当前会话与其他会话摘要 | 单一会话撤销、加载更多 |

首页待办在“待处理 / 等待中 / 已完成”三种状态间切换，一次只展示一种，默认待处理；每种状态保留自己的空态。“开始工作”默认提供两个当前职责最常用且已获权限的入口，不用所有功能卡片填满首页。首页待办的“查看”必须打开对应对象并停留在相关任务，不执行领取、保存、接受或决定。计数必须来自已读取的真实范围；不能把一页的条数写成全部记录总数。

## 5. 渐进披露与表单

### 5.1 三层内容

1. **默认可见：** 当前任务必需的信息、状态、阻塞、决定后果、关键期限与资料可见范围。
2. **详情层：** 完整正文、选中对象依据、需要填写的相关字段、当前版本比较。
3. **补充层：** 完整操作记录、诊断编号、低频选项和技术说明，使用明确的“查看操作记录”“技术详情”等入口。

Apple [Disclosure controls](https://developer.apple.com/design/human-interface-guidelines/disclosure-controls) 建议把常用内容放在最易发现的位置，其他细节在相关时出现。愿作使用与内容相邻的展开入口；不连续嵌套多层折叠，不用一长排独立折叠条来代替页面结构。Apple 对特定 disclosure button 的建议不能误写为整个 Web 页面只能存在一个折叠区域。

字段帮助优先就地使用一句说明，长示例再展开。重要风险和强制声明不放进默认收起的“高级设置”。

### 5.2 画像填写

以下分组只改变呈现，保持现有九个分区和校验关系。页面给出可点击的阶段目录，用户可返回已填写内容；它是引导而非不可退出的强制向导。

| 阶段 | 用户要完成的事 | 现有分区 |
| --- | --- | --- |
| 兴趣与专长 | 说明感兴趣的问题和可提供的能力 | 兴趣与问题偏好、技能 |
| 参与方式 | 说明可投入时间与合作方式 | 可投入时间、协作偏好、地域 |
| 合作边界 | 说明合作成立所需的条件 | 报酬边界、工作边界 |
| 责任与约束 | 说明利益冲突与 AI 使用约束 | 利益冲突、AI 使用约束 |
| 复核与提交 | 核对摘要、缺失项与可见范围，再发布画像 | 以上各区的只读摘要与定位入口 |

已发布画像默认进入阅读摘要。选择“编辑画像”后才呈现字段。“暂停画像”和不可恢复的归档放在明确的状态管理区域；暂停后解释能否继续编辑及如何恢复，不让用户面对无说明的禁用控件。

### 5.3 需求填写

保持现有十三个分区，按完成需求的思考顺序分组：

| 阶段 | 用户要完成的事 | 现有分区 |
| --- | --- | --- |
| 目标与成果 | 说清楚问题、交付内容和判断标准 | 问题与目标、范围与交付物、验收规则 |
| 寻找合作者 | 说清楚需要谁、如何及在哪里一起工作 | 技能、匹配条件、协作偏好、地域 |
| 时间与预算 | 说清楚工期、费用与各阶段安排 | 计划与工期、合成预算、里程碑计划 |
| 风险与授权 | 说清楚数据、AI 与授权 | 风险与数据敏感度、AI 使用约束、授权声明 |
| 复核与提交 | 核对需求摘要及未完成项，再提交审核 | 十三个分区的只读摘要与定位入口 |

“寻找合作者”含四个分区，超过默认预算：这是保持人选条件与地域、协作方式相邻的项目例外。当前采用四个填写阶段加一个复核阶段，与 `web/lib/editor-workflow.mjs` 一致；若实际填写负荷仍高，再按内容拆分，不缩小文字或增加两栏密集输入。

整改入口优先展示本次待修改事项，点选后进入对应阶段并定位字段。仍允许查看完整需求，防止局部修改失去上下文。检查页明确显示本次版本与修改摘要；提交成功后进入“已提交，等待审核”，不继续展示可编辑空表单。

### 5.4 字段规则

- 使用持久标签、简短目的说明和适当的日期、金额、枚举或列表控件。占位符不能代替标签。参见 Apple [Entering data](https://developer.apple.com/design/human-interface-guidelines/entering-data)。
- 字段显示用户熟悉的名称和单位。内部分类代码、条目编号由系统管理；确需辨别时以辅助文本显示，不能要求用户凭空填写 JSON 或猜代码。
- 金额优先用币种和主单位输入，转换为最小货币单位时必须保持精确；在转换能力未实现时，清楚标明现有“分”等单位，不能只改标签而改变含义。
- 已确认的账号、组织和权限信息无需重复手填，但禁止从一个组织身份推断项目授权或替用户填写同意。
- 明确区分必填、选填和不适用。“不适用”在规则要求说明依据时保留原因字段。
- 添加重复项使用“添加交付物 / 添加技能”等内容名称。删除未保存条目可撤回；不可恢复操作另作确认。
- 优先在用户结束编辑字段或点击继续时反馈格式问题，避免输入过程中反复打断。跨分区错误在检查页按阶段汇总，并提供“去修改”。
- 保存、校验、提交是不同动作。“已保存”只在服务端确认后显示；“本标签页草稿”不能冒充服务器保存。
- 当前草稿恢复仅限当前标签页并有既有失效期限。刷新和离开前明确说明可恢复范围，不承诺跨设备自动同步。

## 6. 列表、详情与历史

桌面按内容需要采用“列表 + 详情”，列表承担选择，详情承担理解与行动。Apple [Split views](https://developer.apple.com/design/human-interface-guidelines/split-views) 和 [Lists and tables](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables) 为这种层级导航提供参考。

列表行统一包含可辨识名称、状态、下一步或关键日期。内部 ID 可作为次级识别项，不能占据标题位置。案件或合成账号缺少可披露名称时使用业务类型加短编号；不为改善外观而编造个人信息。

详情头统一包含返回入口、对象标题、当前状态和版本。正文先显示与当前任务有关的内容。历史、版本、管理分别进入明确的页内视图或独立区域；打开历史不在背后留下仍可操作的旧决定表单。

审核队列默认显示“待领取 / 我在处理”，已完成历史通过视图切换进入。不是把三组各几十条记录连续排成一页。无活动分配时不显示空决定表单。

需求全流程默认显示“当前进度”。“参与者”和“操作记录”是同一对象的其他视图；时间线提供阶段与人员筛选、明确的记录范围和“加载更多”。筛选只覆盖已加载记录时必须直接说明，不能让用户误以为已经搜遍历史。原始资料的敏感性不因进入管理员视图而取消。

## 7. 状态、错误和决定反馈

反馈与重要性对应：普通保存结果放在对象附近；需要处理的问题常驻；必须当场决定的不可逆操作使用确认界面。Apple [Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback) 与 [Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts) 支持明确、适度的反馈和能描述结果的按钮措辞。

| 状态 | 用户看到什么 | 可做什么 |
| --- | --- | --- |
| 首次加载 | 当前区域“正在加载需求…”及稳定占位 | 等待；不显示“暂无需求” |
| 空集合 | “还没有需求”及一句解释 | 有权限时“新建需求”，否则说明真实下一步 |
| 无匹配结果 | “没有符合当前条件的候选”及可披露原因 | 按能力查看条件或联系负责方；不推荐放宽安全边界 |
| 读取失败 | “暂时无法更新”及原因摘要 | 重试；旧快照仅在现有安全规则允许时保留并标注时间 |
| 保存成功 | “已保存 · 时间” | 继续或检查；不弹出阻断式对话框 |
| 等待别人 | 当前状态、下一责任角色、已有期限 | 查看依据；不提供无效“继续” |
| 权限变化 | “当前工作区已无法访问这项内容” | 返回可见列表或重新选择工作区 |
| 表单错误 | 页首问题摘要与字段附近的具体错误 | 直接定位并修改 |
| 版本变化 | “内容已有更新，请核对你的修改” | 比较服务器版本和本地修改；不自动覆盖 |
| 写入结果未知 | “尚未确认这次操作是否完成” | 使用原请求确认结果；不换成新的重复提交 |
| 会话失效 | “登录已失效，请重新登录”及草稿实际状态 | 重新登录；重新核对权限后进入可访问内容 |

前台文案采用“发生了什么 → 对当前任务的影响 → 下一步”。例如：

> 这项需求已被其他审核员领取。请返回队列选择另一项。

> 暂时无法确认提交结果。请点“确认上次提交结果”，页面会继续查询同一次操作。

诊断码、追踪编号、ETag 等进入“技术详情”。安全理由、是否成功、数据是否保存以及必须由谁继续不能藏在技术详情里。不会通过“已同步”掩盖读取失败，也不会把未知状态显示为绿色完成。

### 7.1 重要决定

发布、提交、接受邀请、公布决定和管理操作使用具体动词。红色仅用于破坏性或危险操作，不把正常“发布画像”“提交审核”统称为危险按钮。

确认区域在操作前显示对象、当前版本、关键条件、直接后果与可逆性。常规保存不再二次确认；不可恢复归档、撤销访问或关键决定需要明确核对。不得预选同意、让回车默认执行不可逆动作，或用“确定”掩盖操作结果。

当一项写入结果未知时，恢复区优先呈现并防止新的冲突写入。重试沿用既有请求语义和账号范围；UI 重组不能创造新的权限、幂等键或绕过双人独立确认。

## 8. 视觉系统

视觉目标是安静、可阅读、有明确重心的工作工具。层级优先由位置、字号、字重、间距和分隔建立；避免每个分组都用重边框、彩底、大标题与阴影争夺注意力。

以下为愿作建议 token。它们不是 Apple 色板，也不代表当前代码已经逐项采用。保留现有蓝色操作、温和中性色与中文品牌识别，统一为语义化用途。

| Token / 规则 | 建议值 | 用途 |
| --- | --- | --- |
| `canvas` | `#F6F7F9` | 全局背景 |
| `surface` | `#FFFFFF` | 主要内容表面 |
| `surface-subtle` | `#F0F2F5` | 导航或次级信息底色 |
| `text-primary` | `#1D2533` | 标题和正文 |
| `text-secondary` | `#596376` | 辅助说明；不可继续降至难以辨认 |
| `border-subtle` | `#D9DEE7` | 装饰性分隔；不能单独作为必要控件边界 |
| `border-control` | `#7A8493` | 需要识别的输入框与控件边界 |
| `accent` | `#2457A6` | 当前选择和主要操作 |
| `accent-subtle` | `#E8EEF9` | 选中项背景，同时配文字或标记 |
| `success` / `warning` / `danger` | `#176D57` / `#875000` / `#9B3B33` | 状态文字和图标，配明确状态名 |
| `focus` | `#2457A6` | 外侧焦点环，必要时加白色间隔层 |
| 字体 | `system-ui, -apple-system, BlinkMacSystemFont, "PingFang SC", "Microsoft YaHei", sans-serif` | 业务内容统一系统无衬线；品牌字可有个性 |
| 正文 / 辅助 / 小标签 | `16 / 14 / 12–13px` | 小标签不得承载关键说明或长文本 |
| 页面 / 区域 / 组标题 | `28–32 / 20–22 / 16–17px` | 页面只出现一个主标题 |
| 正文行高 | `1.55–1.7` | 支持中文长说明与多行控件 |
| 间距序列 | `4, 8, 12, 16, 24, 32, 48px` | 同组更近、异组更远 |
| 圆角 | 控件 `8px`；内容容器 `12–16px` | 同类组件统一，不把每段正文卡片化 |
| 点击区域 | 默认至少 `44 × 44 CSS px` | 愿作 Web 触控目标，不能与 Apple 的 pt 单位混同 |
| 表单阅读宽度 | 约 `760–880px` | 避免长行和跨屏寻找关联字段 |
| 桌面侧栏 | 约 `220–240px` | 留给内容足够空间 |
| 动效 | `120–180ms` 状态过渡 | 不使用影响阅读的持续动画；尊重减少动态效果偏好 |

正文颜色、按钮文字、输入框边界和焦点需在实际组合中验证对比度，不能只看 token 单值。Apple [Typography](https://developer.apple.com/design/human-interface-guidelines/typography) 与 [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility) 强调可读性和适应用户需要；Web 验收继续沿用仓库既定的 WCAG 2.2 AA 目标。

页面默认浅色；深色模式作为后续完整适配事项，需要同时检查表单、状态、图表、弹层和焦点，不能只翻转背景即宣称完成。高对比度与减少动画的可用性不等待深色模式。

## 9. 响应式与无障碍

### 9.1 空间变化

以下断点是愿作初始设计值，应由实际内容验证：

| 可用宽度 | 布局 |
| --- | --- |
| 大于等于 `1180px` | 固定目的导航；需要时显示列表与详情；长表单仍限制行宽 |
| `760–1179px` | 紧凑侧栏或可收起导航；对象列表与详情优先逐层展开，防止三栏挤压 |
| 小于 `760px` | 单列任务内容；导航用明确标有“工作导航”的菜单；对象详情有返回入口 |

窄屏不把完整桌面侧栏堆在正文上方。需要填写或阅读时首先看到当前任务。当前工作区仍可辨认；长名称换行；按钮在空间不足时垂直排列。步骤目录可横向滚动但当前步骤必须完整可见，或改成“第几步 + 步骤目录”。

数据表仅在比较关系确实需要时保留局部横向滚动，提供可见提示和列标题。整页不得横向溢出。粘性工具栏不得覆盖输入框、错误、页尾内容或移动键盘。

### 9.2 交互可达性

- 提供跳到主要内容、明确的页面标题和正确的标题层级。主导航、主要内容、补充信息具有明确语义。
- 所有按钮、链接、字段和选择器可用键盘访问；焦点顺序与视觉顺序一致。展开、切换和弹层不能丢失焦点。
- 进入新任务时将焦点移到任务标题；返回时恢复到触发项。弹层关闭后返回触发按钮。
- 图标有文字或可访问名称。信息不能只由颜色、左右位置、图形、鼠标悬停或动画传达。
- 表单错误与字段关联；错误摘要可导航；提交后焦点到首个需要处理的问题或结果标题。
- 保存、失败与结果未知使用适当的状态播报；不要让整张页面的每次刷新都被重复朗读。
- 支持 `200%` 缩放，检查 `320px` 窄屏重排，尊重 `prefers-reduced-motion` 与系统高对比度。上述是项目的具体检查条件。
- 一般正文以 `4.5:1`、大字和必要非文本界面以相应 `3:1` 为最低对比度检查线；这些比率来自采用的 [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 标准要求，适用条件按原标准判断，不是对 Apple 的独有归因。
- 日期同时提供清楚的绝对时刻和时区，期限不能只写“明天”。金额带币种；列表可显示简短时间，但决定页给出完整时间。

## 10. 实施顺序与验收依据

### 10.1 先完成结构，再扩展细节

1. **工作壳与导航：** 按目的分组、只呈现当前入口；保留现有账号、工作区、草稿和写入恢复约束。
2. **对象与流程：** 分开列表和详情；首页待办直接定位任务；统一返回、状态、空态、错误与历史入口。
3. **表单：** 按目的分阶段展示现有字段；检查页、整改定位与保存反馈一致；不改变数据合同与领域校验。
4. **角色工作台：** 队列 → 领取 → 详情 → 决定 → 结果；管理员时间线按视图拆分。
5. **视觉与可达性：** 统一 token、间距、按钮层级，检查桌面、窄屏、缩放、键盘和辅助技术。

每一步的实现状态必须用代码与实际验收记录补充。不能把本文的“应当”写成完成事实，也不能把源码字符串测试当作完整浏览器体验的证据。

### 10.2 设计验收

| 检查 | 通过条件 |
| --- | --- |
| 首屏目的 | 不滚动即可辨认当前工作区、当前任务、状态和下一步；等待态可明确没有本人动作 |
| 内容负荷 | 当前只出现一个工作入口；表单只展开当前阶段；补充历史不抢占首屏 |
| 导航 | 每一角色可找到其主要任务；切换入口、打开对象、返回列表都有可预期结果 |
| 决定 | 在提交、响应、确认、裁决前能看到相关对象、条件和直接后果 |
| 状态真实性 | 读取失败不冒充空集合，结果未知不冒充成功，历史不冒充最新详情 |
| 角色独立性 | 两名财务人员分别确认；Trust 独立复核与 Appeal 原决定分离；UI 不扩大权限 |
| 范围真实性 | 接受邀请、完成选择、合成资金确认各自准确；后续未接入环节不装作可操作 |
| 恢复 | 未保存、冲突、结果未知、会话失效后都给出明确路径，并符合现有安全状态约束 |
| 可达性 | 核心任务可全键盘完成，窄屏无整页横向滚动，焦点、状态和错误可被辅助技术理解 |

建议首轮使用合成账号走查以下代表性任务：创作者编辑发布与邀请响应、需求方整改重提、运营领取并释放审核、财务两席确认、组织成员管理、账号状态管理、Trust 独立复核、Appeal 决定、管理员需求时间线。使用 `1440 × 1000`、`390 × 844` 和关键 `320 × 768` 状态检查；这些是项目测试尺寸，不是 Apple 规定。

真实用户研究与真实服务操作仍受现有门禁约束。内部合成任务走查可评价界面是否可操作，不能证明真实用户理解、业务效果或市场需求。

- 浏览器实际验证组织管理员的成员/邀请/组织信息切换，以及独立需求全流程入口；运营审核队列、完成任务自动展开审核历史也通过。
- 在 390px 需求列表和 320px 匹配审核页检查了整页宽度；窄屏功能选择可用，未出现整页横向溢出。
- 本轮浏览器检查没有发起新的业务审核、邀请、资金确认或裁决。输入保留检查仅在本机页面临时修改并恢复原值，没有提交需求变更。以上不是全部角色写入旅程、真实用户研究或完整无障碍审计的证据。

现有页面仍使用同一个 `/app` 工作台内的受控视图；独立可分享业务路由、浏览器前进后退对应业务视图，以及返回列表恢复滚动位置，属于后续导航增强。其余尚未接入的业务能力继续按第 1.2 节处理。
