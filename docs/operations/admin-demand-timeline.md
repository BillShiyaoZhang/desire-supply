# 管理员查看需求全流程

在[当前本机沙盒工作台](https://pilot.example.test)登录平台管理员 `access_admin_01`，或组织管理员 `org_admin_01`，进入对应工作区的“需求全流程”面板，选择要查看的需求。

平台管理员可以查看平台需求；组织管理员只可以查看本组织需求。其他职责不能通过这个入口读取管理员视图。权限由服务端逐次核对。

## 可以看到什么

- 需求的当前状态、所在阶段及需要关注的阻塞。
- 需求编写、运营审核、资金确认、匹配、Trust 与申诉相关的参与者和操作记录。
- 每条记录的发生时间、操作人、职责、动作及可公开的结果详情。
- 项目、合同、里程碑交付、验收和支付等尚未接入的后续环节。

参与人员可以按环节查看，操作时间线可以按环节或人员筛选。历史较多时使用“加载更多操作记录”；筛选针对已经加载的记录。查看期间如果需求有新进展，先“刷新进度”，再继续加载，避免拼接不同时间的状态。

“刷新需求列表”会重新读取可见需求。“刷新进度”重新核对当前需求。切换工作区或重新登录后，先前的数据会清除并按新权限重新读取。

## 如何理解记录

系统从既有的持久化审计和业务事实中汇总记录，因此功能上线前的需求也能查看。记录范围说明会区分完整记录、部分记录和未接入环节；没有保存过的历史信息无法补造。

“已匹配”表示当前匹配流程已完成选择。它不表示已经签约、制作了产品或完成交付。页面继续显示这些后续环节尚未接入。

`tests/pet-feed/` 的演练将原始宠物升降喂食机需求保留为硬件需求，并单独标注用于验证现有流程的软件分析子需求。分类缺口、演练假设和实际执行结果以该目录的报告为准，不能把软件候选的匹配结果当作硬件产品完成。

2026-09-04 21:14–21:15（中国标准时间），上述本机沙盒的真实 HTTP 验收通过：两位管理员各读取软件子需求的 29 条记录、5 位具名参与者；`limit=2` 的 15 页与完整读取一致；6 次非管理员读取均被拒绝；42 份实际响应通过前端生产契约解析。审核原因、列表与详情一致性、未接入环节也已检查。报告和无凭据验收摘要分别保存在仓库的 `tests/pet-feed/REPORT.md` 与 `tests/pet-feed/observed-admin-verification.json`。

## 接口

- `GET /v1/app/admin/demands`：列出当前管理范围内的需求。
- `GET /v1/app/admin/demands/{demand_id}/timeline`：读取单条需求的流程、参与者和操作时间线。

两者都使用当前 Session 和所选工作区，都是只读接口。页面不会通过时间线代替任何角色执行审核、资金确认或匹配操作。
