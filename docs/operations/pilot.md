# 首批项目流程

> 本页提供整体导航。真实运行时，以仓库中的 `mvp/operations/pilot-runbook.md`、`launch-checklist.md`、`data-protection.md` 和 11 份模板为执行清单。

## 批次定义

一个批次包含 5 个进入付费阶段的真实项目，使用同一套冻结规则。建议状态看板：

```text
线索 → 已访谈 → 待补资料 → 资金已承诺 → 匹配中
     → 短沟通 → 已签约 → 进行中 → 验收中 → 完成 / 退出
```

看板只放随机 ID，不放姓名、联系方式、合同或付款凭据。

## 角色责任

| 动作 | 需求方 | 创作者 | 发起人 | 本地工具 |
| --- | --- | --- | --- | --- |
| 问题、预算与验收 | 负责确认 | 提问 | 主持澄清 | 完整性/预算检查 |
| 意愿、能力与边界 | 提供项目上下文 | 负责确认 | 访谈与核证 | 完整性检查 |
| 候选资格与顺序 | 不直接修改 | 不直接修改 | 复核与解释 | 过滤、排序、快照 |
| 邀请与选择 | 双向选择 | 双向选择 | 协调、记录覆盖 | 约束决定记录 |
| 协议、付款与交付 | 按约提供输入/验收 | 按约交付 | 检查节点 | 不处理 |
| 复盘 | 提供反馈 | 提供反馈 | 分开访谈、决策 | 结果和批次报告 |

## 标准流程

### 1. 邀请与预筛

使用统一话术说明这是人工试验、没有公开竞价、不要求免费提案。确认项目在首轮范围：数字化、可分阶段验收、3 天到 4 周、1～5 人可完成、已有预算与决策人。明显违法、高风险专业服务或无法管理的数据项目直接停止。

### 2. 同意与身份隔离

逐项说明数据用途、可见性、保存期限、更正/删除和退出方式。联系人进入独立加密存储，生成随机 ID；之后的 JSON、SQLite、看板和报告只使用 ID。

### 3. 需求访谈

形成问题、目标用户、期望结果、交付与非范围、验收标准、时间、预算、付款、数据和 AI 规则。需求方确认生成的需求卡，不把 AI 或运营者润色当成真实性证明。

### 4. 进入门槛与预算

```bash
uv run mvp import demand demand.json
uv run mvp validate demand <id>
uv run mvp budget <id>
```

`BLOCKER` 未解决不得匹配；`RED` 必须调整范围或预算；`YELLOW` 只有在范围和报酬仍合理时书面留痕。资金证据保存在外部受控位置，数据库只保存引用。

### 5. 创作者访谈

确认兴趣、边界、容量、协作偏好、私密报酬底线和 AI 规则。至少核实一项能力证据，并分别确认哪些资料公开、仅匹配使用或完全私密。

### 6. 匹配与人工复核

```bash
uv run mvp match <demand-id> --top 3
uv run mvp explain <demand-id> <creator-id>
```

复核所有硬过滤原因和前三名分项。新上下文应先修正资料并重新运行；不得在决定阶段恢复硬过滤候选。

### 7. 分别确认披露

先询问创作者是否愿意接收匿名需求，再分别确认双方可交换的字段。发送前检查没有身份、私密底线、内部风险标签或第三方私密反馈。

### 8. 有目的的短沟通

限定 30～45 分钟，只解决说明中的未知和风险。禁止索要免费方案、样稿或大量测试。会后分别记录接受/拒绝及标准原因，不互相转述私密原话。

### 9. 决定留痕

```bash
uv run mvp decision <demand-id> \
  --selected <creator-id> \
  --invited <ids...> \
  --responses responses.json \
  --reason <code>
```

未成交时省略 `--selected`。邀请与规则顶部不同，需要选择标准覆盖原因；`OTHER` 必须补充最小必要事实。

### 10. 协议与开工

在选定的有效签署工具中确认范围、非范围、交付物、验收、价格、变更、取消、知识产权、保密、数据和 AI 条款。首个里程碑资金保障确认后才开工。协议与付款材料不进入本数据库。

### 11. 协作、变更与验收

每周检查需求方输入、风险、交付与付款。范围增加使用书面变更单，同时确认价格和时间；交付按约定验收。口头决定当天写入共享记录。

### 12. 退出访谈与结果

完成或退出后 7 天内分别访谈双方，记录事实、再次合作意愿、安全事件和发起人分环节耗时。

```bash
uv run mvp outcome <project-id> --file outcome.json
```

### 13. 批次复盘

第五个付费项目后生成报告：

```bash
uv run mvp report <pilot-id>
```

结合失败案例和原始访谈，选择“继续人工验证 / 只产品化一个瓶颈 / 调整方向 / 停止”。不要只凭漏斗百分比自动进入开发。

## 批次报告读法

报告把证据分为七组：

- `funnel`：访谈需求、资金承诺、匹配、选择、签约、真实付款和完成；
- `matching`：前三名命中、人工覆盖原因和候选响应原因；
- `budget_status`：最新推荐的 GREEN/YELLOW/RED 分布；
- `delivery`：里程碑、按约付款、范围变更、争议和需求清晰度；
- `experience`：双方再次使用、创作者偏好得到确认、服务费接受；
- `operator_hours`：招募、访谈、匹配、协调和争议耗时；
- `concentration`：机会与收入 HHI、各匿名创作者收入，以及失败/安全事件。

报告中的 H1～H6 是方向性阈值，不是统计结论。五个项目样本无法证明因果；应逐条回看推荐快照、覆盖原因和分开访谈。HHI 越高表示机会或收入越集中，但小样本和不同项目金额会强烈影响它，不能单独作为处罚或自动调权依据。

## 服务标准

- 所有参与者使用同一组核心问题和进入门槛；
- 24 小时内确认收到关键提交，不能按期处理时给出新时间；
- 每个需求默认邀请 1～3 人，拒绝不损害后续机会；
- 只分享当前决定必需的资料，新用途重新获得同意；
- 发起人与任一方存在利益关系时，在匹配前向双方披露；
- 规则在批次中冻结，项目中途只修阻塞性错误和安全问题。

## 立即停止与升级

出现未授权披露、可疑身份/付款主体、资金承诺撤回、骚扰/歧视/威胁、明显违法、高风险专业要求或不可管理的数据风险时，立即暂停相关项目。停止扩大传播，保全最小必要证据，按事件响应流程分级通知和处置。
