# Foundations 实现差距审计

> 文档状态：临时代码与设计审计记录 v0.1。审计日期为 2026-08-09，检查对象是提交 `6789db6` 之上的未提交工作区；该工作区没有独立 snapshot，不能由提交号完整重建。本文描述审计时观察，不是上线声明、可永久继承的能力基线，也不替代安全、法律、财务或组织审查。

## 0. 结论先行

当前仓库已经证明了两件事：第一，礼宾式 MVP 能以随机 ID、身份字段隔离、确定性规则和可解释记录帮助运营者完成需求校验、预算闸门、匹配、人工选择和结果记录；第二，目标平台已经在身份、租户、权限、政策同意、会话安全、规则目录、Creator Profile、Demand、Matching 和 Outbox 等基础域上建立了相当严格的契约、领域模型和一部分 PostgreSQL 实现。

但它距离 foundations 描述的愿作仍然很远。最准确的判断不是“还缺一些页面”，而是：

> 现有代码主要证明了若干安全基础设施和交易前半程可以被严谨建模；它尚未证明一段完整协作可以在线完成，更没有证明成员共同体、公共经济、共同治理、退出重建和使命保护能够真实运行。

主要差距如下：

1. `mvp/` 是可运行的本地运营工具，不是多用户平台；身份、合同、沟通、付款、争议和同意仍由线下人工或外部系统承担。
2. `platform/` 呈现“横向基础很深、纵向产品不通”的状态：局部领域有大量契约和数据库测试，但没有从登录、发布、匹配、项目、付款到结果复盘的生产级闭环。
3. foundations 的核心制度——正式成员成长、公共劳动、公共基金、成员经济权益、宪法级治理、核心资产守护、合法分支和反异化评价——大多还没有成为一等技术能力。
4. 当前架构文档远远走在实现前面，且不同页面的状态说明已有漂移。单一的“GREEN”无法说明一个能力究竟只完成领域测试，还是已经完成 PostgreSQL、HTTP、组合、启用、运营和效果验证。
5. 最重要的限制不在代码：所有权、资本边界、法律实体、劳动与税务关系、成员主权和外部社会保障不能由数据库自动实现。软件只能让制度可执行、可审计、可申诉，不能代替制度本身。

因此，近期不应把“治理平台”作为孤立功能优先建设。更合理的顺序是先完成一个窄而真实的有偿协作闭环，证明参与者愿意再次合作；再把真实发生的公共劳动、权利冲突和成员责任逐步制度化。完整路径见[Foundations 落地路线图](/foundations/realization-roadmap.md)。

## 1. 审计范围与证据口径

### 1.1 审计范围

本次检查覆盖：

- `docs/foundations/` 中的社会契约、经济宪法、成员与开放共同体设计；
- `mvp/` 的源码、配置、Schema、样例和测试；
- `platform/` 的契约、源码、迁移、运行组合和测试；
- `docs/architecture/` 中各目标领域的设计与当前实施边界；
- 当前工作区的测试结果。

没有把文档中的未来时设计、类定义或测试文件名自动算作“已实现”。也没有把一次测试通过自动解释为现实制度有效。

审计时 `platform/` 及多份目标架构页面仍是未跟踪工作区内容，因此提交 `6789db6` 只是仓库基线，不能单独重建本次被审计快照。正式发布能力状态前，应先形成可复现 revision，并重新运行测试与证据采集；本文中的精确数量不得永久继承到后续版本。

### 1.2 能力状态必须分层

此后每项基础能力至少要分别记录以下状态，不能再用一个总括的“完成”或“GREEN”：

| 层级 | 判断问题 |
| --- | --- |
| `DESIGN` | 边界、不变量、威胁和失败语义是否写清楚 |
| `CONTRACT` | 命令、事件、数据契约和兼容策略是否固定 |
| `DOMAIN` | 领域规则是否有可执行模型与单元测试 |
| `MEMORY` | 应用流程是否在内存适配器中闭合 |
| `POSTGRES` | 事务、并发、RLS、迁移和恢复语义是否由真实数据库验证 |
| `HTTP` | 身份、授权、幂等、错误和隐私是否穿过真实传输边界 |
| `COMPOSED` | 真实适配器是否由生产组合根连接，而非只在测试中手工拼装 |
| `ENABLED` | 能力是否在某个受控环境打开，并有关闭、降级和回滚路径 |
| `OPERATED` | 是否已有人员、职责分离、运行手册、告警和事件处置经验 |
| `EFFECTIVE` | 真实结果是否支持 foundations 的目标，且没有不可接受的副作用 |

例如，存在 `Vote` 聚合和单元测试只能证明 `DOMAIN`，不能证明民主治理已经 `EFFECTIVE`；有数据导出接口也不能证明成员拥有现实可用的退出与重建能力。

### 1.3 四类要求

Foundations 中的主张需要按实现责任分类：

| 类型 | 含义 | 例子 |
| --- | --- | --- |
| 软件可强制执行 | 正确输入和权限下，系统可以稳定阻止或保证 | 硬边界过滤、禁止未授权读取、章程冷静期、职责分离 |
| 软件支持、人作决定 | 系统提供证据、工作流和审计，但不能代替判断 | 同行评议、争议裁决、成员资格审查、公共项目评选 |
| 法律与组织制度 | 需要真实法律实体、合同、董事责任或财务安排 | 成员经济权益、使命信托、资本权利边界、资产转让限制 |
| 外部社会条件 | 愿作只能倡导或合作，不能单独提供 | 全民医疗、住房、基本收入和完整的转型安全网 |

这一区分是整个技术规划的边界。否则很容易用一个表决页面代替共同治理，用一个推荐算法代替公平，用一份导出文件代替退出自由。

## 2. 当前实现事实

### 2.1 礼宾式 MVP：可运行，但定位明确受限

`mvp/` 是本地、确定性、运营者驱动的命令行工具。它的成熟之处包括：

- 对需求的决策权、资金承诺、范围、验收、预算、付款计划、风险、数据敏感度和 AI 边界进行结构化校验；
- 对创作者的意愿、技能证据、可用性、最低报酬、合作偏好和明确边界进行结构化表达；
- 在匹配前执行预算与硬边界闸门，不允许人工选择直接绕过硬过滤；
- 以确定性规则和活动规则版本产生当次可重复的匹配结果，保存不可变推荐快照；标准候选说明不直接输出私密报酬原值，但完整匹配分项仍有推断风险；
- 记录邀请、选择、覆盖理由和项目结果，包括运营自报的付款、里程碑、范围变更、争议、安全事件和再次合作意愿；
- 使用随机 ID、受控引用、本地 SQLite 和迁移/恢复机制，主动拒绝明显的姓名、邮箱、电话、微信和地址字段；这属于去标识化尝试，不是匿名保证。

这些机制在方向上呼应“真实需求先于撮合”“边界先于成交”“技术可解释且由人负责”，也提供了邀请/响应的技术胚芽；但双向接受尚未成为系统不变量，历史规则与解释也不能完整重演，因此只能说流程意图部分对齐。审计时 `mvp` 的 134 项测试全部通过。

但 `mvp/local-data/` 没有真实项目记录，仓库样例明确是虚构数据。因此上述结果只证明工具行为，不证明需求真实性、付款公平、拒绝无报复或参与者愿意再次合作。

但 MVP 只把这些价值编码成输入字段、配置、闸门和运营记录。它没有真正承担：

- 账户、组织、身份核验、Consent 和权限；
- 线上协议、交付、验收、资金托管、付款与对账；
- 沟通、文件、举报、Safety Hold、争议、申诉和独立复核；
- 数据权利请求、完整可携带导出和可验证贡献证明；
- 成员成长、公共贡献、治理、公共基金或使命保护。

因此 MVP 适合继续产生制度证据，不适合被描述为 foundations 的产品实现。

### 2.2 目标平台：严格的局部切片，尚无完整产品路径

`platform/src/desire_platform/` 目前实际存在的主要模块是：

- `identity_access`：身份、组织租户、角色、政策同意、Consent、会话和部分生命周期；
- `taxonomy`：受控代码、规则目录及版本；
- `creator_profile`：Creator Profile、版本与字段披露；
- `demand`：Demand 生命周期、版本和发布前规则；
- `matching`：匹配尝试、运行、邀请与选择的一部分；
- `outbox`：事务事件出站；
- `http`：以 IAM 为主的协议和传输适配；
- `runtime`：配置与组合状态机的纯内核。

这些模块已经形成大量契约、内存实现和 PostgreSQL 测试，尤其重视 fail-closed、租户隔离、RLS、幂等、并发和未知提交结果。这是正确的安全方向。

但以下目标域还没有独立 bounded context、公开契约、应用与持久化闭环：Project/Agreement、Workspace/File、Funding/Payment、Trust/Safety/Dispute、Notification、Data Rights、Audit/Analytics、Controlled AI Gateway、Community/Governance、Public Commons，以及使命与资产守护。仓库已有少量前置原语，例如 SafetyHold port/test double、Demand 的 FundingSecured marker、Profile/Demand 的 AI 标志和跨命令 audit/outbox；它们不能被当作对应目标域已经实现。

审计时 `platform` 共运行 646 个顶层测试方法，产生 43 条 failure record；失败记录集中在 PostgreSQL 持久会话安全的 13 个语义测试方法及其 subtest：会话能力视图、重放标记、保留密钥查找、会话族撤销与收敛、连接池复用/所有权及 ACL/RLS 等仍未闭合。总测试目标仍然是红色，不能用局部通过数对外宣称平台可发布。

### 2.3 架构设计与代码事实必须分开

现有架构文档已经详细设计了许多未来领域，但大多数仍停留在 `DESIGN`：

| 领域 | 审计判断 |
| --- | --- |
| IAM、政策同意、权限、read model | 多个 `DOMAIN/MEMORY/POSTGRES` 切片和 21-operation protocol/ASGI/presenter registry 已完成；持久 Session 的 PostgreSQL 安全语义仍为 RED，真实 IdP、concrete server/production binding、proxy/TLS 和浏览器闭环未完成 |
| Taxonomy | 领域、应用和 PostgreSQL 较完整；跨上下文消费者、HTTP 与生产组合未闭合 |
| Creator Profile、Demand | 领域与 PostgreSQL 切片存在；HTTP、组合和真实用户路径未闭合 |
| Matching | 领域与内存切片存在；PostgreSQL、RLS、HTTP、完整选择组合和后续项目创建未闭合 |
| Outbox、Runtime | Outbox delivery worker、PostgreSQL repository/inbox 与纯组合内核存在；缺生产 broker adapter、具体 consumer projection、独立进程装配、厂商 E2E、发布恢复和灾备演练 |
| Project、Funding、Safety、Data Rights、Audit、AI、Community、Web | 主要是架构设计，没有对应源码与端到端证据 |

还存在文档状态漂移。例如 Creator Profile 与 Demand 的总览页仍写数据库未完成，而各自 PostgreSQL 专页和实际代码已经前进；项目结构页也没有完整反映现有模块。状态漂移不是文案小问题，它会直接导致错误排期、重复实现和错误上线判断。

### 2.4 审计发现的具体正确性与权利风险

下列问题不是“未来可以再做”的一般功能缺口，而是演进前需要明确处置的当前风险。MVP 的单机、单运营者、去标识化试点边界可以降低部分攻击面，但不能消除数据权和事实完整性问题。

严重度使用 `Critical` 和 `High`，避免与路线图的 P0/P1 阶段混淆。`Critical` 阻断相关能力接触真实数据或生产启用；`High` 必须在目标平台发布前关闭，并在礼宾试点中用明确人工护栏控制。

| 严重度 | 当前证据 | Foundations 风险 | 设计要求 |
| --- | --- | --- | --- |
| Critical | MVP 每次推荐把全部 Creator 完整 Profile，包括不活跃、不合格和无关候选，复制进不可变快照；个体删除依赖重建整个批次库 | 数据最小化、目的限定、个体更正/删除与审计不可变性直接冲突 | 快照只保存决定所需最小事实；稳定审计与可更正/可删除载荷分层；建立按主体定位和处置能力 |
| Critical | 匹配输出包含 compensation 分项，结合公开预算区间和公式可能反推出私密报酬底线；现有泄漏检查主要检查原值字符串 | “私密底线不披露”没有形成抗推断保证 | 对输出做信息流/推断威胁建模；不发布可逆分项；用属性测试与人工红队验证 |
| Critical | MVP 的身份检测主要检查字段名，自由文本仍可写入姓名、电话或邮箱；小样本 CSV 可输出逐创作者收入 | 伪匿名与小样本再识别 | 自由文本扫描/人工复核、导出授权、小样本抑制、受控环境和明确保留策略 |
| Critical | 单个本地运营者可以导入资料、改规则、发邀请、选人、写 Outcome 和出报告，没有 actor、权限、复核或申诉 | 人工最终负责退化为单点隐藏主权 | 在迁移到多用户环境前建立身份、职责分离、覆盖理由、访问审计和复核；试点期也需线下责任台账 |
| High | MVP 允许缺少候选 response 仍记录 selected；“selected 属于 invited”并不等于候选明确 `ACCEPT` | 双向选择目前是操作承诺，不是系统不变量 | 双方接受是建项前置；拒绝、超时、撤回和重新邀请有明确状态机 |
| High | Schema 合法与生命周期未分开；字段齐全的 `cancelled` Demand 仍可能被匹配 | 已退出/取消主体可能被重新投入机会分配 | 每个命令同时校验数据、生命周期、授权和当时有效规则 |
| High | MVP Outcome 的“真实支付”“按约付款”是自报布尔值，未与签署、里程碑、应付、实付和对账交叉验证，跨字段状态也可能矛盾 | 报告把访谈记录误当财务事实 | 标明证据等级；最终支付只由 Funding/Payment 对账事实产生，访谈作为独立观察保留 |
| High | Recommendation 不可变；Decision 经 CLI/repository 为 insert-only，但 SQLite 无 update/delete 防护，直接数据库操作仍可改；Outcome 原地 upsert；历史只保存规则版本字符串，解释由当前代码重生成 | 历史决定、报告和理由可能被静默改写 | 数据库约束与访问边界共同保护；决定/Outcome 版本化或更正事件；保存规则内容摘要、配置哈希和解释器版本 |
| High | JSON Schema、`schema.py`、validation 和模板是重复合同，已有状态和值域漂移；部分匹配规则读取的字段无法由合法 Demand 提供 | 文档、校验和执行可能对同一事实给出不同答案 | 建立单一机器合同或自动等价验证；每项硬规则必须有可达契约测试 |
| High | MVP 的收入 HHI 把已支付里程碑金额等分给相关创作者，机会 HHI 由 Outcome 而非邀请/曝光事实推导；Markdown 报告突出漏斗、top3 和服务费接受，却未呈现已计算的集中度 | 使命指标可能产生虚假确定性，并被增长指标反向塑造 | 指标绑定权威事件源、证据等级、样本阈值和限制说明；使命指标与财务指标并列；方向性估算不得冒充事实 |
| High | Decision 保存时会排序 invited IDs，报告却用该顺序与推荐 top3 比较；已有 `is_override()` 未被采用，reason code 也未与真实覆盖状态绑定 | 正常选择可能被误报为人工覆盖，污染责任与使命指标 | 覆盖事实由统一领域函数产生；报告消费决定事实而非重新推断；增加顺序和理由一致性测试 |
| High | Creator 没有 pilot、tenant 或用途 Consent scope；匹配从全局集合读取，兴趣强度为 0 仍可能得到重合分，`direct_cost` 也不参与预算/匹配 | 去标识化数据跨目的复用，且“有偏好字段”被误解成主动愿意与可持续报酬 | 所有 Profile 披露绑定目的/租户/时限；主动意愿和可持续成本分别建模，不能从加权分数推断 |
| Critical | 平台全量测试的 43 个失败记录集中在 PostgreSQL IAM Session v2：重放族撤销、保留密钥、CSRF 重新授权、连接池/ACL/RLS 和未知结果收敛等 | 真实浏览器会话和生产 HTTP 边界不能成立 | 保持该能力关闭；逐项闭合安全语义、真实 PG/池和组合证据后再宣称可用 |
| High | Demand 契约和事件描述资金申请，但源码缺少正式的 `VERIFIED → FUNDING_PENDING` 命令；Matching 结果也没有闭环回写 Demand | 契约存在制造“流程已实现”的错觉 | 用可调用命令、聚合转换、消费者和端到端测试证明状态链，不以 OpenAPI/事件名代替实现 |
| Critical | Matching 发布邀请时从工作单元全局取首个 Selection，未按 `attempt_id` 过滤 | 可能把另一匹配尝试的选择用于当前邀请，破坏隔离与决定完整性 | 在启用前修正聚合/查询作用域，并以多 attempt 并发与租户隔离测试验证 |
| High | Matching 的若干失败/关闭/过期命令未接入 dispatcher，选择只写 intent，仓库没有 `CompleteSelection`；`CompleteMatchRunCommand.candidate_results` 的 component scores/exclusions 由外部传入，应用只重新校验并确定性排序/hash | 领域类存在但真实流程不可达，Demand→Project 断裂 | 以公开入口和完整纵切验收每个状态，不把未 dispatch 的类计为可用能力 |
| High | IdP 与 SafetyHold 只有 ports 和严格 test doubles，broker 生产源码只有 publisher protocol；没有 production provider adapter、具体进程入口或生产组合 | 测试中的成功不能证明现实依赖和故障语义 | 生产组合缺依赖即启动失败；真实 provider 契约、降级、重试、恢复和演练分别留证 |

## 4. 批判性评价

### 4.1 优点：当前工程方向多处与 foundations 一致

现有实现没有使用竞价排名、公开私密报酬原值、不可解释黑箱模型或以交易额换取权限。它在 Schema 和领域边界上主动追求数据最小化、明确边界、人工责任、不可变事实、租户隔离和失败关闭；上文发现的全量快照、推断泄漏等问题说明这项追求尚未完整兑现。方向仍然值得保留，但必须由信息流和端到端证据校正。

### 4.2 主要结构性问题：基础设施深度超过了价值闭环

当前平台在 IAM 和 PostgreSQL 安全语义上投入很深，但还没有一条用户能完成的完整协作链。继续横向铺开更多领域设计，会扩大“文档很完整、产品不可验证”的落差。

下一阶段的技术中心应从“再完成一个孤立上下文”转为“完成一条最窄的生产纵切”：真实身份与 Consent → Profile/Demand → 受控匹配与双方确认 → Agreement/Milestone → 资金确认与付款 → Outcome/Review → 权利请求与审计。只有这条路径存在，才可能观察 foundations 所关心的尊严、公平、关系和公共价值。

### 4.3 概念模型偏交易，制度主体仍缺位

当前核心主体仍是 User、Organization、CreatorProfile、Demand 和 Match。Foundations 还要求另一组不能由“用户角色”替代的主体：正式成员资格、有任期的守护者/代表职务、代表机构、公共金库、章程、核心资产、贡献凭证和合法分支。它们有不同的资格、责任、期限、申诉和法律含义。

尤其要避免把 CommunityGroup 的 `MEMBER/REVIEWER/STEWARD` 角色直接等同于共同体公民身份。前者是某个小组内的访问和工作角色；后者涉及跨群体政治资格、公共责任和宪法程序。

### 4.4 “能记录”不等于“能保障”

- 记录拒绝不代表拒绝不会降低未来曝光；还要验证推荐和运营决策没有隐性惩罚。
- 保存匹配解释不代表机会公平；还要观察集中度、首次机会和不同群体的结果。
- 提供投票不代表成员有权力；还要有信息、提案、审议、预算、执行追踪、申诉和退出。
- 提供数据导出不代表能离开；导出还要可理解、可验证、尊重第三方权利并能被其他系统接收。
- 保存贡献不代表公共劳动受到支持；还要有资金、责任人、资格、冲突规则和结果问责。
- 代码中禁止资本角色不代表资本不能控制组织；控制通常发生在股权、债务、董事席位、关键客户和现金流依赖中。

### 4.5 过早自动化治理会制造新的技术官僚制

成员资格、贡献价值、公共项目和章程解释都存在合理分歧。若在真实成员关系形成前把它们写成积分、阈值和自动状态机，系统会把创始团队的早期偏好冻结成看似中立的规则。

因此，初期系统应优先保存证据、理由、异议和时限，让明确授权的人作可复核决定；只有反复出现且边界稳定的部分才适合自动强制执行。任何贡献加权投票、全局声誉分、自动封禁、自动成员晋级和算法化公共预算都不应成为默认方案。

## 5. 对已有模块需要的改动

这里描述目标责任，不等于立即开发清单。具体依赖见[技术能力地图](/foundations/technical-capability-map.md)。

| 现有模块 | 应保留 | 为 foundations 需要扩展 | 不应承担 |
| --- | --- | --- | --- |
| Identity & Access | 租户隔离、Consent、权限、会话与审计边界 | 区分账户、组织角色、共同体公民身份和有任期的公共职务；支持资格投影而非把成员规则塞进 IAM | 不决定谁“贡献足够”，不成为经济权益或章程真相源 |
| Taxonomy & Rule Catalog | 受控代码、版本、兼容与发布 | 纳入匹配、费率、成员资格、评审、公共资金和宪法程序的规则包；增加影响分析、异议与生效证据 | 不让通过 Community 投票的提案直接修改生产规则 |
| Creator Profile | 意愿、边界、Evidence 引用、`VERIFIED` 发布检查、证据快照和字段披露 | 补齐证据 ingest/verify/revoke 生命周期；增加目的限定共享、当前相关性、可携带证明和拒绝不惩罚的审计信号 | 不维护全局声誉总分或自动政治资格 |
| Demand | 决策权、预算/资金声明、验收、风险闸门和外部 FundingSecured 投影 | 补齐资金请求与失败/替代流程；区分商业需求与公共价值需求；连接协议、Safety、结果和公共影响 | 不把支付能力当作问题价值或治理权 |
| Matching | 硬边界、确定性、快照、解释和邀请/响应记录的技术胚芽 | 持久化/RLS/HTTP；真正的双向接受；增加机会集中度、新人探索、冲突排除、规则影响模拟和可申诉决定 | 不独立决定资格、处罚、付款或“谁更有价值” |
| Outbox & Runtime | 原子事件、现有 delivery worker、PostgreSQL repository/inbox、幂等消费者和配置失败关闭 | 将现有 worker/PG repository 接入生产 broker、具体 consumer 与独立进程；补齐跨域追踪、组合、降级、恢复和规则/章程版本固定 | 不以事件最终一致性绕过资金或治理的强一致边界 |

## 6. 必须新增或明确独立边界的能力

现有目标架构中的 Project、Funding、Safety、Data Rights、Audit、AI 和 Community 仍需实现；Foundations 还提出了五组当前设计不足的新边界：

1. **Membership & Civic Roles**：Membership 管理参与者、贡献者、正式成员的资格、证据、续期、暂停、退出和申诉；Public Office 独立管理守护者、代表和评审者的任期、培训、补偿、回避与轮换；二者与组内角色、IAM 权限和经济权益解耦。
2. **Commons & Public Fund**：管理公共劳动登记、预算来源、拨款轮次、申请、利益冲突、集体决策、付款授权、成果与公开报告；不能被普通交易 Funding 模型吞并。
3. **Charter & Mission Stewardship**：管理章程版本、宪法事项分类、核心资产登记、重大变更、跨机构批准、冷静期、反对意见、资源集中度和合法分支包；法律效果必须由真实实体与合同承载。
4. **Contribution Credentials & Portability**：生成有来源、领域、时间、角色和第三方权利边界的可验证贡献证明；支持纠错、撤销、选择性披露、导出和跨共同体验证，不形成可交易总分。
5. **Member Economic Rights Projection**：从法定实体与财务账簿投影成员受益资格、不可转让权益、剩余分配、对账单和退出处理；严格分离经济受益权、政治表决权与产品权限，不能由贡献积分自动生成。

Community 领域可以继续负责小组、知识、贡献提交、同行评议和普通提案，但不应独自拥有上述所有制度。否则它会成为一个无边界的“共同体巨石”。

## 7. 当前最高风险

| 风险 | 现在的表现 | 控制方向 |
| --- | --- | --- |
| 文档幻觉 | 设计页数量和细节容易被误认为代码事实 | 建立分层能力登记册，以测试、迁移、组合和运行证据逐层晋级 |
| 永远没有纵向闭环 | 不断补基础设施和未来上下文 | 下一阶段只以完整有偿协作旅程作为主交付单位 |
| 把规范变成积分 | 贡献、成员和公平很容易被一个分数代替 | 证据优先、叙事展示、人工复核、期限与申诉；默认禁止总分 |
| 把法律问题软件化 | 代码角色被误认作成员所有权和使命锁 | 法律/组织工作流与软件投影分开验收 |
| 运营者成为隐藏主权者 | MVP 的人工覆盖没有完整权力约束 | 原因码、双人复核、利益冲突、审计、申诉、超时与透明报告 |
| 治理先于共同体 | 没有稳定成员却先实现复杂投票 | 以真实责任和公共劳动作为激活门槛，先做小组级试验 |
| 指标反向塑造行为 | 成交、活跃和增长吞噬使命指标 | 使命指标成组解释，公开口径，定期质性复盘和反游戏化审查 |
| 退出只有形式 | 导出文件不可用、含第三方数据或没有接收方 | 开放格式、可验证凭证、选择性导出、接收演练与合法分支预案 |

## 8. 审计后的优先判断

1. 先修复能力状态事实和当前平台的测试红线，不新增“已完成”叙事。
2. 以一条真实、受控、有偿协作闭环作为所有基础设施的共同消费者。
3. 把权利、安全、付款、申诉和审计放在增长功能之前，因为它们决定参与者是否真的有能力拒绝和离开。
4. 在真实公共劳动出现后，再实现成员资格与贡献凭证；在稳定正式成员出现后，再激活代表治理和公共基金。
5. 从 P0 起就用临时法律与组织护栏限制融资、客户条件、数据和核心资产处置；在真实成员与治理证据成熟后，再把成员经济权益、宪法程序、核心资产守护和合法分支接入完整法律结构。
6. 每一阶段同时交付软件证据、运营能力、法律边界和效果指标；任何一项缺失都不得声称 foundations 已实现。

下一步所需的完整技术边界见[Foundations 技术能力地图](/foundations/technical-capability-map.md)，实施顺序与激活门槛见[Foundations 落地路线图](/foundations/realization-roadmap.md)。
