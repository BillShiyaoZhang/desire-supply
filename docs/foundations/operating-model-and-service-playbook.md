# 运营模型与服务手册

> 文档状态：P0/P1 运营基线草案 v0.1  
> 适用范围：`G0B` 外部真人研究只使用本文的 Research/Privacy/Ethics/补偿/投诉子集，并以独立研究库结束；全流程服务蓝图和封闭有偿试点只在 `G2` 后适用。不适用于公开市场、正式共同体治理或公共金库。  
> 激活条件：研究子集须先逐项通过 `G0B`；真实服务则须由责任角色、时限、批次上限、联系路径、外部专业结论和完整演练共同通过 `G2`。本文本身不授权任一 Gate。  
> 核心原则：人工负责不等于人工可以任意决定；每个重大决定都要有权限、证据、理由、期限、复核和补救。

## 0. 运营目标

首批运营不是临时替代品，而是用最小规模验证一项服务是否真实成立。运营团队负责：

- 阻止模糊、无资金、无授权或不公平需求进入匹配；
- 保护创作者表达意愿、边界和拒绝；
- 让角色、协议、变更、付款和结果可理解；
- 在软件失效时继续维护报酬、数据权、申诉和善后；
- 记录隐形劳动、例外、伤害、反例与运营成本；
- 让后续自动化只发生在边界稳定、证据充分的环节。

运营不负责替代律师、会计师、持牌支付机构、外部服务机构或实际受益者作权威判断。

## 1. 创始期授权结构

### 1.1 必备角色

下表是 `G2` 真实服务批次的完整角色集。`G0B` 研究只任命统一 Gate 要求的研究责任实体/负责人、Privacy/Security、Ethics/Legal、补偿/财务、投诉/安全和替补；若某个服务角色在研究活动中没有相应动作，不得为了“填满表格”赋予它生产、项目或资金权限。

| 角色 | 主要责任 | 不能同时承担 |
| --- | --- | --- |
| Pilot accountable | 批次范围、容量、预算、总体暂停和阶段报告 | 自己批准自己的重大风险例外 |
| Product accountable | 产品范围、术语、用户验收和变更控制 | 以路线压力覆盖安全/法律阻断 |
| Demand reviewer | 核验问题、角色授权、范围、验收、预算与排除项 | 审理与本人审核相关的最终申诉 |
| Creator steward | 保护创作者知情、边界、邀请与拒绝；检查关系性强迫 | 代表需求方选择候选 |
| Match/Case coordinator | 组织有限邀请、同意、协议、输入、沟通和状态 | 修改硬边界或替任一方默示接受 |
| Payment initiator | 依据已批准义务发起资金操作 | 独自核实同一付款最终成功 |
| Finance reconciler | 核验 provider/银行/法定账簿事实、退款和异常 | 独自批准自己发起的付款或例外 |
| Safety & dispute lead | 接收举报、施加最小临时保护、调查和初次决定 | 处理自己或直接上下级涉案的申诉 |
| Independent appeal reviewer | 检查程序、证据、冲突和补救 | 参与原决定、项目选择或付款争议的初次处理 |
| Privacy contact | 数据清单、访问、更正、删除、限制、导出和事件协调 | 未经授权兼作营销或匹配数据使用决定人 |
| Legal/Compliance accountable | 维护专业意见、合同版本、辖区和禁区 | 用产品状态代替法律判断 |
| Research lead | 同意、研究质量、证据等级和偏差复核 | 把研究资料默认用于匹配或声誉 |
| Security/Operations responder | 访问、事件、恢复、供应商故障和技术暂停 | 在缺少业务/权利负责人时单独关闭全部权利 |

同一自然人可在小规模下兼任不冲突角色，但以下分离不可取消：

1. 高风险付款的发起与最终核实；
2. 原决定与申诉复核；
3. 有利益冲突的候选选择与资格/争议审查；
4. 规则制定、重大例外和对该例外的最终审计；
5. 研究联系人身份库与广泛分析访问；
6. 伙伴资源控制与参与者独立投诉处理。

若人数不足以满足分离，应缩小或暂停试点，不得用“创业早期”作为无限例外。

### 1.2 授权登记

真实服务批次前必须填写；`G0B` 研究只为其获批子集填写：

```text
Role:
Primary person:
Backup:
Authority source/version:
Allowed actions:
Forbidden actions:
Maximum financial/data/participant scope:
Conflict rules:
Training completed:
Availability and contact route:
Start/expiry:
Reviewer:
```

角色到期、请假或冲突时，权限及时撤回，但已取得报酬、申诉、数据权和历史证据不能无关失效。

## 2. 批次前置检查

Pilot accountable 在每个真实服务批次开始前确认；真人研究使用启动入口的 `G0B` 清单，不以本表替代：

| 检查项 | 必须结果 |
| --- | --- |
| 产品范围 | ICP、项目类型、地域/辖区、币种、金额、人数和排除项已批准 |
| 参与者保护 | 招募、知情说明、拒绝/撤回、投诉和补救资金可用 |
| 合同与支付 | 当前合同、签署主体、付款/退款/税务路径和 provider 已批准 |
| 数据 | 字段清单、用途、访问、保留、删除、导出和供应商已批准 |
| 运营 | 所有角色和替补可达，工作队列和 WIP 上限已配置 |
| 安全 | 事件分级、紧急联系、最小保护、证据保存和通报路径已演练 |
| 工程 | 固定版本、环境、备份、恢复、降级、功能关闭和人工接管已验证 |
| 财务 | 批次预算、潜在退款/补救、支付余额和损失上限已落实 |
| 风险 | 本批次触发的 Critical 已关闭，或已有 Gate 前控制且残余影响不再为 Critical；High 仅在法律、`FND-*` 和最低控制满足后接受残余风险 |
| 宣称 | 招募和说明材料没有夸大匹配、收入、公平、所有权或治理效果 |

任一项缺失，批次状态为 `BLOCKED`。不得让已经招募的参与者承担团队准备不足的成本；若需延期，应主动说明并提供退出和相称补偿。

## 3. 服务蓝图

### 3.1 阶段 1：招募、知情与资格

**输入**：获批准的招募范围、说明材料、Consent/隐私版本。  
**负责人**：Research lead 或 Creator/Demand steward。  
**步骤**：

1. 确认招募来源不存在未披露的权力关系；
2. 说明试点性质、未知风险、费用/补偿、数据、退出和投诉；
3. 参与者逐目的选择，录音、公开案例、营销和匹配披露不得打包同意；
4. 只核验本批次必要资格，不建立完整生活或站外关系图；
5. 保存同意版本和证据，提供副本与撤回路径。

**暂停信号**：无法现实拒绝、未成年人/脆弱参与者缺保护、招募承诺与真实服务不一致。  
**输出**：若为 `G0B` 研究，仅在独立研究库保存最小 Research Subject/Evidence、作用域明确的 Consent 和招募/利益冲突来源，并在研究活动结束后停止，不创建产品 Participant 或进入阶段 2；若为 `G2` 服务，才输出 Participant、服务 Consent 与后续资格事实。

### 3.2 阶段 2：需求核验

**输入**：Demand 草案和角色责任矩阵。  
**负责人**：Demand reviewer。  
**最少核验**：

- 最近一次真实问题、受影响者和不解决的成本；
- 问题提出者、实际受益者/代表、决策、出资、资源、候选选择、验收和协调的授权；
- 范围、必要输入、排除项、时间、成果路径、验收和维护/移交；
- 预算、税费口径、付款责任和资金保障方式；
- 数据、AI、IP、保密、行业和人身安全风险；
- 是否存在无偿样稿、无限修改、雇佣伪装、关系性强迫或不当控制。

**决定**：`APPROVE / REVISE / REJECT / ESCALATE`。  
**输出**：版本化 Demand、理由、责任人和适用规则。  
**禁止**：为增加项目数量降低硬边界，或让创作者免费完成实质需求澄清。

### 3.3 阶段 3：创作者资料与目的限定披露

**负责人**：Creator steward。  
**步骤**：

- 分开意愿、能力证据、边界、可用性和可持续成本；
- 让创作者选择哪些字段向本次匹配、需求方或运营者披露；
- 检查自由文本 PII、第三方资料和陈旧/争议证据；
- 确认提高效率不会被简单按工时压价；
- 明确拒绝、撤回和更新方式。

私密报酬底线只用于必要闸门，不进入候选说明、分项分数、导出或可逆推结果。

### 3.4 阶段 4：匹配、邀请与选择

**负责人**：Match/Case coordinator；Creator steward 保护创作者选择。  
**步骤**：

1. 固定 Demand/Profile/规则版本和最小必要输入；
2. 执行硬边界、冲突和资金闸门；
3. 形成有限候选并由授权人员检查异常，不得覆盖硬边界；
4. 每名候选独立收到范围、报酬、时间、风险和披露说明；
5. 候选明确 `ACCEPT/DECLINE/WITHDRAW`，沉默不等于接受；
6. 获授权选择者只从已接受候选中决定，并记录理由和冲突；
7. 任何重新邀请使用新状态，不修改历史。

**质量抽查**：定期检查拒绝者后续机会、人工覆盖、候选集中度和不当压力。  
**禁止**：公开投标、出售排名、批量向所有人施压或要求创作者解释私人拒绝理由。

### 3.5 阶段 5：协议、资金与开工

**负责人**：Case coordinator、Legal/Compliance accountable、Payment initiator 与 Finance reconciler。  
**开工前清单**：

- 所有必要合同当事人或获授权签字人接受同一 AgreementVersion；
- 范围、成果、输入、时间、里程碑、报酬、税费、验收、修改和终止明确；
- IP、署名、作品展示、许可、第三方素材、保密和成果维护明确；
- 受益者成果确认与合同验收的关系明确；
- 数据控制/处理、文件、消息、保留、AI 和导出边界明确；
- 退款、冲正、付款失败、争议和外部救济明确；
- 需要保障的资金由权威来源核实为 `SECURED`；
- 联系、升级、申诉和退出方式可理解。

任一必要方未接受、资金只处于请求状态或合同主体不明，项目不得开工。

### 3.6 阶段 6：交付、输入与范围变化

**负责人**：Case coordinator。  
**规则**：

- 输入请求、交付和验收均引用里程碑与版本；
- 延迟由谁导致、如何影响时间与成本，先记录事实再判断责任；
- 实质范围、成果路径、时间或报酬变化形成新版本与重新接受；
- 小修正与实质变更的边界在协议中预先说明；
- 不通过私聊、文件覆盖或口头承诺静默改变事实；
- 安全或争议只限制必要动作，保留无关资料、报酬和救济。

### 3.7 阶段 7：验收、付款与对账

**负责人**：验收人、Payment initiator、Finance reconciler。  
**步骤**：

1. 验收人按当时有效标准 `ACCEPT / REJECT_WITH_REASON / REQUEST_CONTRACTED_REVISION`；
2. 实际受益者或代表按约提供独立成果确认；
3. 已接受义务进入付款授权，发起人与核实人分离；
4. provider 请求、处理中、到账、退款、冲正和未知结果分别记录；
5. 只有权威对账事实可以标记最终 `PAID`；
6. 参与者获得可理解的付款/扣费/税费说明；
7. 异常进入财务队列，不用重复付款“试试看”。

平台不得未经专业确认持有、混同或挪用参与者资金。

### 3.8 阶段 8：结果、评价、关闭与退出

**负责人**：Case coordinator、Research lead、Privacy contact。  
**步骤**：

- 双方分开记录事实、体验、再次合作意愿和不愿公开的内容；
- 财务事实、运营判断、参与者自报和受益者反馈分开；
- 记录实际成果路径、许可、公共回流、维护/移交或有理由停止；
- 评价有回应、更正、争议和选择性披露；
- 关闭项目不删除应付报酬、申诉或法定数据权；
- 告知保留、导出、删除/限制和未来邀请设置；
- 记录运营工时、公共劳动、异常和未决伤害。

## 4. 决定记录与人工覆盖

所有影响机会、范围、报酬、付款、数据、安全或申诉的人工决定使用同一最小格式：

```text
Decision ID / type:
Subject and affected rights:
Actor / authority / role term:
Conflict check:
Source facts and versions:
Applicable policy/contract versions:
Decision and effective scope:
Reason code + necessary explanation:
Alternatives considered:
Duration / expiry:
Notice delivered:
Review/appeal route and deadline:
Second approval（若适用）:
Audit/evidence references:
```

候选理由码只用于聚合与发现，不替代事实说明。运营者不能通过自由文本创造未发布的新政策。

## 5. 最小安全、争议与申诉包

真实试点前必须具备本节能力；路线图 P2 负责扩展和可靠化，不得把本节推迟到真实伤害发生后。

### 5.1 可报告事项

- 骚扰、威胁、歧视、报复、欺诈、冒名、利益冲突和关系性强迫；
- 未授权数据披露、私密底线推断、第三方资料滥用；
- 无偿试作、恶意压价、范围失控、拒收和付款争议；
- IP、署名、保密、成果用途和公共资产争议；
- 运营者越权、规则未公开、选择/资格/申诉程序不公；
- 技术、安全、支付或伙伴停摆造成的权利不可达。

### 5.2 事件分级

| 等级 | 示例 | 首要动作 |
| --- | --- | --- |
| `SEV-0` | 现实人身危险、重大欺诈/资金损失、活跃数据泄露、跨租户访问、全部权利不可达 | 立即保护人、限制最小风险范围、通知负责人、保存必要证据、停止新增相关流程 |
| `SEV-1` | 报复、骚扰、重大付款/范围争议、未授权披露、利益冲突或权力强迫 | 在批准时限内确认受理、指定无冲突负责人、评估临时保护和通知 |
| `SEV-2` | 普通服务错误、理解问题、非重大延迟或资料更正 | 进入服务队列、说明预计步骤并跟踪完成 |

具体响应时限、法律通知和外部报告义务在 `G2` 前填写。没有已批准时限不得启动真实批次。

### 5.3 正当程序

1. **接收**：允许站内外渠道，提供回执和安全联系偏好；
2. **风险分流**：先保护人和资金，不以是否有完整证据拒绝紧急评估；
3. **临时措施**：目的有限、范围最小、自动到期，不预判最终责任；
4. **冲突检查**：涉案者、上下级、资金关系和直接竞争者回避；
5. **证据清单**：只收集必要材料，记录来源、完整性和第三方权利；
6. **通知与回应**：在不增加伤害的条件下，让受影响方知道指控范围并有机会回应；
7. **决定**：适用规则、事实、证明限制、理由、措施、期限和修复分别写清；
8. **补救**：可包括更正、重新验收、重新决定、付款/退款、恢复访问、道歉、培训、限制、终止或外部转介；
9. **申诉**：由未参与原决定的人复核事实、程序、冲突和相称性；
10. **关闭与复盘**：通知结果，检查报复和系统性原因，必要时修改流程。

无法保密处理的范围应在收集敏感举报前告知。匿名举报可以触发调查，但不自动证明责任。

## 6. 数据权利运营

真实批次前至少提供：

| 请求 | 处理责任 | 最低动作 |
| --- | --- | --- |
| 知情/清单 | Privacy contact | 说明数据类别、用途、来源、对象、保留和影响 |
| 访问 | 各域 owner + Privacy contact | 核验身份，汇集可理解副本并过滤第三方权利 |
| 更正 | 事实 owner | 新版本/更正事件，不静默改写历史决定 |
| 限制/反对 | Privacy + 业务 owner | 暂停可停止用途，说明必要处理和复核路径 |
| 删除 | 各域 owner | 分项处理法律保留、合同、第三方、provider 和备份水位 |
| 导出 | Privacy + 各域 owner | 开放格式、完整性、说明、第三方过滤和接收验证 |
| Consent 撤回 | Consent owner | 新处理停止，说明既有合法处理和后果，不实施机会报复 |

请求入口、身份核验、法定/承诺时限、队列、积压、失败、升级和结果通知必须在 `G2` 前演练。不能只提供一个邮箱而无人负责。

## 7. 财务控制

- Demand 审核、资金确认、候选选择、付款发起、付款核实和财务审计按风险分离；
- 每笔资金记录合同/项目/里程碑、付款义务、金额币种、税费口径、provider ID、状态和对账证据；
- 未知、重复、迟到、部分、失败、退款、拒付和冲正分别有 runbook；
- 不从分析报表或运营自报反写最终付款事实；
- 参与者资金、平台收入、公共资金和风险准备不得混同；
- 批次开始前落实退款、纠错和参与者补救的资金来源；
- 日终/批次对账、差异阈值和升级责任在 `G2` 前批准；
- 任何可能构成代收付、托管、贷款、证券或受监管金融活动的安排先由专业人员确认。

## 8. 伙伴与线下项目附加手册

使用高校、社区、园区、企业、基金会、公共服务或场地资源时，每个伙伴版本必须记录：

- 问题、实际受益者和代表授权；
- 出资、资源、决策、候选选择、验收、协调和数据角色；
- 资金、品牌、报告、IP、署名、场地、设备和安全条件；
- 参与者拒绝加入、拒绝特定导师/托管方或非必要数据后，站外待遇不受影响的证明；
- 相称替代路径、独立联系人和绕开伙伴的申诉；
- 无障碍、保险、紧急事件、设备损坏和现场责任；
- Handoff 的提出、本人同意、提交、外部接受/拒绝、撤回、到期和关闭；
- 伙伴退出或节点停摆时的项目、报酬、数据权、凭证和申诉承接者。

外部机构仍是其资格、场地和服务是否实际交付的权威来源；愿作不能把“已转介”写成“已获得服务”。

## 9. 沟通与通知

重大通知必须包含：发生了什么、当前状态、需要谁在何时做什么、不行动的后果、联系人、复核/申诉和版本。通知不是事实真相源。

禁止：

- 用紧迫倒计时迫使接受项目、条款或数据用途；
- 向需求方披露创作者私人拒绝理由；
- 在争议未决时公开暗示责任；
- 用营销渠道发送付款、数据或安全敏感内容；
- 只在应用内发送影响权利的通知而没有批准的备用通道；
- 把批量未读、退信或失败投递视为已知情。

## 11. 业务连续性与人工接管

至少演练：

- 应用不可用时如何读取当前协议、关键联系和应付义务；
- 身份 provider 故障时如何避免越权并提供安全支持；
- 支付 provider 未知或停摆时如何冻结重复操作、继续对账和告知参与者；
- 伙伴退出时如何承接项目、资料、申诉和外部服务联系；
- 运营负责人不可用或涉冲突时替补如何接管；
- 数据泄露时怎样限制访问、保留必要证据、评估通知并防止二次传播；
- 备份恢复后权限撤销、删除水位、审计和付款状态是否仍正确；
- 停止试点时如何完成已有义务、退款/付款、数据处置和参与者说明。

手工台账只用于受控连续性，不得成为未经权限、无备份或无限保留的影子数据库。

## 12. 培训与质量保证

真实批次前，各角色至少完成：

- 社会契约、禁止结果和服务范围；
- Consent、最小数据、敏感信息和研究边界；
- 需求与角色授权核验；
- 双向接受、拒绝无报复和关系性强迫；
- 协议、范围变化、付款状态和证据等级；
- 举报、临时保护、正当程序、回避和申诉；
- 安全事件、恢复和停止试点；
- 反歧视、无障碍与清晰语言；
- 不可对外宣称的能力和指标限制。

质量抽查至少覆盖：全部 Critical/SEV-0 案件、高风险付款与例外、所有申诉、随机 Demand/邀请/变更/关闭案例，以及拒绝后的机会趋势。抽查者不能只检查表单是否填写，还要检查参与者是否实际理解和得到补救。

## 13. 试点暂停、结束与阶段报告

### 13.1 可暂停新增项目的角色

Pilot、Safety、Privacy、Finance、Security、Legal accountable 均可在自己职责范围内暂停新增相关流程；恢复需要原风险关闭证据和指定批准，不得由业务增长负责人单方覆盖。

### 13.2 立即暂停条件

- 现实人身危险或参与者无法安全退出；
- 未授权数据访问、跨项目/租户泄漏或私密底线可推断；
- 付款/对账无法收敛或补救资金不足；
- 重大法律/合同主体不确定；
- 拒绝、举报或申诉后出现报复；
- 原决定与独立复核无法分离；
- 运营积压导致报酬、申诉或数据权超过批准时限；
- 伙伴强迫参与或把外部待遇与愿作身份捆绑；
- 软件故障使协议、报酬或权利没有可用人工接管。

### 13.3 批次结束报告

报告采用[落地路线图](/foundations/realization-roadmap.md)第 11 节模板，并额外记录：

- 实际招募来源与退出；
- 每个队列的数量、时限、积压和人工工时；
- 付款、退款、未知、冲正和补救事实；
- 拒绝、范围变化、争议、举报、申诉和数据权请求；
- 运营覆盖、利益冲突和质量抽查；
- 双方和受益者的独立反馈、反例与未决伤害；
- 价格、单位服务成本和继续承担能力；
- 明确建议：继续、缩小、修改、保持人工、回滚或停止。

完成项目数量不是唯一目标；一项被安全拒绝、及时停止或公正补救的项目同样提供关键制度证据。
